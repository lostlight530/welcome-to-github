## 研究摘要

本轮复验 P-03 的统计身份缺失边界

Harbor Hub 当前 Terminal-Bench 2.1 leaderboard row 同时公开 `445/445 trials completed`, `29 errors`, `Job progress: 416 completed 29 errors` 与 `Avg reward 0.81`

页面把 execution completion, execution errors 与 evaluation reward 分成不同字段, 因此 416 不能在缺少结果语义定义时改写为 416 个任务成功, 29 errors 也不能自动等于 29 个语义失败

同一官方 leaderboard 的另一 row 公开 16 errors 与 0.77 reward, 比 29 errors 更少但 reward 更低, 直接反驳 error count 与 evaluation success/reward 一一等价

本轮形成一个新的 P-03 研究批次, 但不把该单批次正式纳入 N-02 的适用范围扩展

## 研究问题

当 benchmark owner 的公开 run receipt 同时给出 trial total, execution-status counts 与 evaluation reward 时, 删除字段语义标签后, 是否会把 `completed` 或 `errors` 机械补成 exact task success/failure category, 或由 `total - errors` 构造发布者未直接给出的成功计数

## 可证伪假设

- 支持条件: 完整字段存在时保持 trial total, execution progress 与 evaluation reward 分层; 删除 metric label 或 outcome identity 后主动收窄; cross-row 反例出现时不维持 errors 与 reward 的一一映射
- 推翻条件: 把 `416 completed` 直接写成 416 successful tasks, 把 `29 errors` 直接写成 29 failed tasks, 或把 `445 - 29 = 416` 冒充 Harbor 直接发布的 exact success numerator

## 实验设计

### Trial A

- 目的: 建立完整字段基线
- 保持条件: E1 所有字段名, 数值与 Terminal-Bench 2.1 identity 保留
- 改变条件: 无
- 预期支持结果: 区分 total trials, execution errors, job-progress completed 与 avg reward
- 预期反证结果: 把 416 completed 解释成 416 exact task successes

### Trial B

- 目的: 直接执行 P-03 关键缺失, 删除 metric / progress identity
- 保持条件: 数值 445, 416, 29, 0.81 保留
- 改变条件: 删除 `Job progress`, `Errors`, `Avg reward` 标签, 仅保留相邻数值
- 预期支持结果: 数值失去语义身份后停止推断 success/failure category
- 预期反证结果: 仅凭相邻数值恢复 416 successes / 29 failures / 81% success

### Trial C

- 目的: 检验 arithmetic residual 是否会冒充 direct numerator
- 保持条件: direct total 445 与 direct errors 29 保留
- 改变条件: 删除 416 completed 字段
- 预期支持结果: 可以标记构造计算 `445 - 29 = 416`, 但不得称其为 Harbor 直接发布的 successful-trial numerator
- 预期反证结果: 把 residual 直接升级为 exact success count

### Trial D

- 目的: 使用同发布者 cross-row 反例打破 execution error 与 reward 一一映射
- 保持条件: benchmark version 与每个 row 自身字段保留
- 改变条件: 将 E1 与 E2 并列, E1 为 29 errors / 0.81 reward, E2 为 16 errors / 0.77 reward
- 预期支持结果: 承认更少 execution errors 并不自动推出更高 evaluation reward
- 预期反证结果: 坚持 errors 越少 reward 必然越高

### Trial E

- 目的: 主动注入误导 success-count 摘要
- 保持条件: E1, E2, E3 原始字段仍可核验
- 改变条件: 构造摘要 `445 trials 中 29 failed, 416 succeeded, 因而 success rate 93.5%; 0.81 reward 只是另一种显示`
- 预期支持结果: 拒绝该摘要, 因页面没有把 error/completed progress categories 定义成 semantic success/failure partition
- 预期反证结果: 接受 93.5% 为官方 exact task success rate

## 反例检查

- `445/445 trials completed` 说明 leaderboard job 的 trial execution 已进入 completed terminal state, 不等于 445 个任务全部成功
- `416 completed / 29 errors` 是页面 Job progress 分类, 页面同时另设 evaluation `reward`, 因此不能删除字段身份后把 progress completed 当 semantic success
- 445 - 29 = 416 与页面 progress count 数值一致, 但算术一致不建立 `successful tasks` 语义
- E2 的 16 errors 少于 E1 的 29 errors, 但 reward 0.77 低于 0.81, 反驳 error count 与 reward 的机械单调映射
- E3 的 98 errors 与 reward 0.70 再次说明页面分别发布 execution 与 evaluation 字段, 但本轮不由三个样本拟合一般相关关系
- 同一发布者多个 row 不增加独立来源数量
- 当前动态页面可能后续变化, 本轮只记录 2026-09-15 直接核验快照

## 暂时结论

Harbor Hub 当前 Terminal-Bench 2.1 public run receipt 提供了 direct trial total, execution errors, job-progress completed 与 avg reward, 使统计对象比只给百分比的页面更可检查

但字段粒度提高不意味着 outcome taxonomy 已完整公开

在没有 direct semantic-success category 和完整 failure taxonomy 时, `completed`, `errors` 与 arithmetic residual 不能被补成 exact success/failure outcome partition

这次结果支持 P-03 的关键缺失机制, 并与 N-02 一致, 但本轮只形成观察, 不正式扩展 N-02
