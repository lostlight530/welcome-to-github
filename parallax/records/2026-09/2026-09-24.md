## 研究摘要

本日研究长期 Agent 在 deliberation 期间持有的工具清单是否可以被当成稳定 capability identity. 直接核验 MCP 当前公开 SDK 文档后，得到一个有边界的观察: tool discovery 是时间相关状态，且 2025-era 与 2026-07-28 protocol revision 的 change-delivery 机制不同. 因此早先读取到的工具清单不能自动充当 action-time executable capability 证明.

## 研究问题

当 Agent 在时点 S0 取得 MCP 工具清单，而服务端在行动前改变工具集合时，S0 的 discovery snapshot 是否足以证明 S1 行动时仍具有同一 executable tool capability?

## 可证伪假设

- 支持条件: 官方协议或 SDK 材料明确允许工具集合在运行时改变，并要求通过特定 change mechanism 重新获得 current list, 因而 S0 snapshot 与 S1 executable capability 必须分离
- 推翻条件: 当前协议材料明确保证连接生命周期内工具集合不可变化，或保证任意 S0 tools/list snapshot 在后续 action-time 无条件继续有效

## 实验设计

### Trial A

- 目的: 检查 legacy-era 的 S0 tools/list 是否可能因 runtime tool registration 变旧
- 保持条件: 同一 MCP tool-discovery object, 同一 publisher family
- 改变条件: server tool registry 从未包含目标工具变为 runtime 注册目标工具
- 预期支持结果: 文档要求 list-change signal 后重新读取 tools/list 才能观察新工具
- 预期反证结果: 文档声明初始 tools/list 在连接生命周期内不可变化

### Trial B

- 目的: 检查 modern 2026-07-28 lifecycle 中 change awareness 是否还依赖 subscription state
- 保持条件: tool-list change object 与 publisher family
- 改变条件: protocol revision 与 client subscriptions/listen opt-in state
- 预期支持结果: modern change delivery 仅经已打开且被确认的 subscription stream 到达
- 预期反证结果: server 对所有 clients 无条件广播 tools/list_changed, 不依赖 subscription state

## 原始观测

1. MCP Python SDK 当前文档给出 runtime `add_tool` 后通知 tool-list change 的示例，并说明 client 随后再次调用 `tools/list` 才看到新工具.
2. 同一页面明确区分 legacy connection 与 2026-07-28 connection: modern connection 的变化通知只在 client 自己打开的 `subscriptions/listen` stream 上接收.
3. MCP TypeScript SDK migration 文档说明 2026-07-28 的 tools/prompts/resources list changes 只经 `subscriptions/listen` 交付，且 client 配置与 server-advertised capability 共同约束实际订阅集合.
4. MCP Ruby SDK subscriptions 文档进一步说明 `toolsListChanged` 是 subscription filter 项，server 首先确认 honored subset.
5. 本轮没有运行 MCP client/server，没有取得任何具体 Agent host 的 notification trace 或 invocation trace.

## 反例检查

首选解释可能被反例 `initial discovery is sufficient because tool changes are always pushed automatically` 推翻. 当前 2026-07-28 SDK 文档反而限定了通知路径: client 必须通过 `subscriptions/listen` 请求对应 change type，且实际 honored subset 受 server capability 约束. 因而 `server changed tool registry` 本身不能推出 `client learned the change`.

另一个反例是 `notification received == refreshed executable capability`. 本轮没有证据证明收到 list-change notification 后 client 一定成功重新读取列表，更没有证明后续 tool invocation 或 semantic outcome 成功，因此拒绝该等价关系.

## 暂时结论

当前状态为观察. 在本轮直接核验的 MCP public contract 中，tool inventory 具有 temporal identity. 对长期 Agent 而言，S0 discovery snapshot 不能自动证明 S1 action-time capability. 至少需要保留 protocol revision, change-subscription state, refreshed discovery state 与 invocation outcome 的区分.

该结论只覆盖公开协议/SDK contract，不证明任一具体 host 的实现正确性，也不升级为 CASE 或 NOTES finding.

## AGI-scale relevance boundary

长期自主 Agent 可能在较长 deliberation, delegation 或 recovery 周期中持有 tool plan. 如果 tool inventory 在此期间变化，而系统仍把旧 snapshot 当成 current capability，计划可在执行时失效或错误归因. 本轮只研究 epistemic freshness 与 configuration identity，不构成任何 AGI capability claim.
