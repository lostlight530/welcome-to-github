## 研究摘要

OpenAI Status 的 2026-09-14 Agents API 事件直接记录 managed sessions 从 delays or unable to start turns, 经 mitigation recovery, 到 Resolved 时 processing turns normally 的同事件时间链

当前 OpenAI API reference 同时保留 managed agent session 对象与 `POST /agents/sessions` 创建契约, 但该 living reference 不是 2026-09-14 incident window 的 runtime sample

本轮直接执行 P-04 时间替换核心变化: 删除时间锚时不再把三个状态排成确定先后, 删除 Agents API / managed sessions 身份时不把事件状态扩大到全部 OpenAI API 或全部 agent execution

## 研究问题

当同一官方 production incident 对同一 managed-session 对象给出影响状态, recovery 与 resolved terminal state 时, 判断能否随较新事件状态更新, 同时保留较早影响状态为历史, 并在时间锚或对象身份被删除后主动收窄

## 可证伪假设

- 支持条件: 完整事件时间链下更新 current incident judgment 到 Resolved, 保留较早 delays / unable-to-start-turns 状态; 删除时间锚后停止确定状态顺序; 删除对象身份后停止把事件状态扩大到其他 API 或全部 agent execution
- 推翻条件: 删除时间锚后仍声称确定恢复顺序, 删除 managed-session 身份后仍把状态外推到全部 OpenAI API, 或把事件级 Resolved 改写为每个 individual session 都成功且持续无故障

## 历史背景

P-04 当前定义要求旧状态与更新状态具有明确生效时间, 更新当前判断时保留历史原因

2026-09-07 已记录 workspace connector write-action incident 的 aggregate recovery, 2026-09-08 已在 Railway 中记录新的发布者 disable→re-enable transition, 2026-09-14 已记录 Terminal-Bench 2.0→2.1 revision chronology

当前下一复验方向包含 public runtime switch 与另一 production object 的 per-object terminal state, 本轮选择 Agents API managed sessions, 不重复上述对象
