## 研究摘要

Terminal-Bench 2.1 官方 release 将自身定义为 Terminal-Bench 2.0 的 revision, 明确修复 89 个任务中的 28 个

官方页面把修订问题分为 external dependencies, resource mismatches 与 misspecification, 并明确给出多个相同 agent×model pair 在 2.0 与 2.1 上的成对 accuracy

例如 GPT-5.3-Codex with Codex CLI 从 73.3% 更新为 79.1%, GPT-5.4 with Codex CLI 从 76.0% 更新为 77.3%, Gemini 3.1 Pro with Terminus 2 从 63.0% 更新为 70.7%, Opus 4.6 with Claude Code 从 58.0% 更新为 70.1%

这些成对结果补齐 2026-09-06 FrontierMath correction 当时缺失的 same-model performance rerun 类型条件, 但本轮仍保持两个边界

第一, 2.1 的较新结果更新 current benchmark-version judgment, 不删除 2.0 作为旧版本真实历史结果

第二, benchmark task contract 已改变, 因此 2.0→2.1 score delta 不能直接写成模型能力本身的 causal improvement

## 研究问题

当 benchmark owner 明确发布 2.0→2.1 revision chronology, 修复 28/89 tasks, 并对相同 agent×model pair 给出新旧版本成对 accuracy 时, 是否会更新 current benchmark-version judgment, 同时保留 2.0 历史结果与修订原因

删除 version chronology 或 correction scope 后, 是否会把剩余的两组分数自动解释成同一 benchmark 上的模型能力变化, 或把旧版本结果物理视为无效事实

## 可证伪假设

- 支持条件: 完整基线将 2.1 视为较新 benchmark contract, 保留 2.0 历史分数; 删除 version chronology 后拒绝确定新旧替换关系; 删除 correction scope 后只保留版本间数值差异而不归因具体修复机制; 注入 `模型能力提升` 或 `旧分数应删除` 摘要时保持拒绝
- 推翻条件: 在缺少 2.0/2.1 version identity 时仍确定哪组数值是当前 benchmark result, 将 12.1 percentage-point delta 直接归因为 Opus 4.6 模型更新, 或因 2.1 发布而删除 2.0 曾真实报告的历史结果

## 实验设计

### Trial A

- 目的: 建立 2.0→2.1 revision chronology 与 paired agent×model rerun 完整基线

- 预期支持结果: current benchmark judgment 更新到 2.1, 2.0 结果保留为历史, score delta 不写成模型能力 causal improvement
- 预期反证结果: 因 2.1 较新而删除 2.0 历史结果, 或把 paired delta 直接归因模型本身

### Trial B

- 目的: 直接执行 P-04 核心变化中的时间与版本身份删除

## 反例检查

- 2.1 fixes 28/89 tasks 不表示 2.0 从未真实存在, 旧版本分数仍属于其当时 benchmark contract
- paired score 上升不能单独证明底层模型 weights, provider route 或 agent implementation 在两个运行间发生能力提升
- `Opus 4.6 + Claude Code 58.0%→70.1%` 是跨 benchmark version 的同 pair comparison, 不是同一未变 benchmark 上的 12.1pp model-only causal estimate
- 并非每个 changed task 都改善, E1 的 task-level chart包含 negative differences, 因此 `所有修订都提高分数` 不成立
- 28 个 changed tasks 包含 external dependency drift, resource mismatch 与 misspecification, 不能把所有变化压缩为单一 bug 类型
- current 2.1 leaderboard 不能倒写成 2026-05-06 paired rerun 当时的完整运行环境
- current submission rule 禁止修改 timeouts/resources, 不能自动证明历史 paired runs 的所有 hidden config 完全相同
- 本轮没有运行 benchmark, 正式 release table 不能冒充本轮 runtime sample

## 暂时结论

在本轮受控输入中, Terminal-Bench 2.0→2.1 提供了 P-04 之前缺少的一类独立 benchmark correction: benchmark owner 明确发布 revision chronology, 说明 correction scope, 并同时给出相同 agent×model pair 在修订前后的成对 performance

因此 current benchmark judgment 可以前向更新为 2.1, 但 2.0 paired scores 继续保留为对应旧版本的历史事实

同一 pair 的 score delta 证明 benchmark-version change 与 measured outcome 同时发生, 不足以把全部差异归因为底层模型能力变化

这一观察与 N-03 既有 `较新有效证据更新 current judgment 但不删除历史` 边界一致, 本轮作为复发检查, 不正式扩大 N-03 长期适用范围
