## 研究摘要

OpenAI Status 当前保留的事件页记录, 2026-04-29 页面显示 Identified 时, some ChatGPT workspace connectors 的 write actions 被自动禁用, OpenAI 正在恢复 affected write actions, 同时 workspace admins 可从 connector settings 的 action control 手动重新启用 write permissions

同一事件页在 2026-05-05 页面显示 Resolved, 并明确写明 all impacted services have now fully recovered

OpenAI Help Center 当前文档进一步说明, 对支持 Action control 的 app, 管理员可允许全部 actions, 仅允许 read actions 或选择 custom actions, 新 actions 也可按策略启用或禁用; 部分 app 不支持 Action control

因此本轮能够直接核验一个同对象 disable→recovery 时间链与当前事件终态, 但不能把事件终态解释为每个 connector 的当前配置位均为 enabled

这直接执行 P-04 的旧状态与较新状态时间替换核心变化, 并首次对当前优先的 true bidirectional on/off 方向形成部分满足的受控复验

## 研究问题

当同一官方状态事件先记录 connector write actions 被自动禁用, 后记录 impacted services fully recovered, 且当前管理文档仍允许 action-level 配置时, 是否能把当前事件判断更新为 resolved, 同时保留自动禁用曾发生的历史事实

删除 terminal update, 时间锚点或 action-control 适用边界后, 是否会补出永久禁用, 全部 connector 自动开启或逐 connector 当前状态

## 可证伪假设

- 支持条件: 完整材料下将 2026-04-29 自动禁用保留为历史事件状态, 将 2026-05-05 fully recovered 作为该事件的当前终态, 当前 action control 继续按支持范围与 workspace 配置解释; 删除关键状态或时间后相应收窄, 不补出逐 connector runtime state
- 推翻条件: 把 2026-04-29 自动禁用改写为永久禁用, 把 2026-05-05 fully recovered 改写为所有 connector write actions 当前必然 enabled, 删除时间后仍断言精确生效顺序, 或忽略部分 app 不支持 Action control 的当前文档边界

### Trial A

- 目的: 建立 disable→recovery 完整时间替换基线
- 保持条件: E1 event identity, Identified/Resolved 两阶段, 页面显示时间与 E2 current action-control boundary
- 改变条件: 相对历史 P-04 材料换用新的 workspace connector write-action incident
- 预期支持结果: current incident judgment 为 Resolved / fully recovered, 同时保留 write actions 曾自动 disabled 的历史状态
- 预期反证结果: 删除历史 disabled 状态, 或拒绝采用较新的 resolved terminal update

### Trial B

- 目的: 检查 terminal update 是否是当前事件判断的必要证据

- 改变条件: 从构造输入中删除 E1 Resolved / fully recovered 更新

### Trial C
