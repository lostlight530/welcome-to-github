## 研究摘要

本日研究一个 state-continuity shortcut: 只要下一次运行使用相同 session identifier，是否就足以证明 conversation history 已经 durable recovery.

OpenAI current Agents SDK contract 明确要求 interrupted run 恢复时同时保持相同 session identity 与相同 underlying storage backend；其 SQLiteSession 默认使用 in-memory database，process 结束后数据丢失，只有 file-backed 或其他 durable backend 才改变 persistence contract.

Google current agents-cli contract 又明确 local session 位于 running server memory；要跨 separate runs resume，需要保持 background server 存活. 同一 CLI 还把 `in_memory`, `cloud_sql`, `agent_platform_sessions` 作为不同 session storage 类型暴露出来.

因此本轮得到 bounded result: logical session identity 是 lookup coordinate，不是 durability proof. 当前证据足以否定 session-ID-only inference，但不足以证明任何具体 production system 已成功或失败恢复状态.

## 研究问题

相同 session identifier 是否足以证明 conversation history 在 process/server lifetime 变化后仍可恢复，还是 durable continuity 还依赖 storage backend 与 runtime-lifetime contract?

## 可证伪假设

- 支持条件: 至少两个独立 publisher 的当前合同允许相同 logical session identity 在不同 backend 或 server/process lifetime 下产生不同 persistence behavior

## 实验设计

### Trial A

- 目的: 测试相同 session identity 是否能够覆盖 storage-backend 差异
- 保持条件: OpenAI Agents SDK session abstraction 与 logical session ID
- 改变条件: in-memory SQLite backend 对比 file-backed persistent SQLite backend
- 预期支持结果: persistence behavior 随 backend 改变，而不是由 session ID 单独决定
- 预期反证结果: 两种 backend 在 process restart 后都由相同 ID 无条件恢复相同历史

### Trial B

- 目的: 测试 local session identity 是否能够覆盖 server lifetime 差异
- 保持条件: Google agents-cli local run 与 `--session-id` continuity interface
- 改变条件: one-off server shutdown 对比 `--start-server` 保持 background server 存活
- 预期支持结果: local session resume 依赖 running server lifetime
- 预期反证结果: server 结束后仅凭同一 session ID 仍由 local in-memory state 无条件恢复

### Trial C

- 目的: 跨 publisher 检查 identifier 与 durability 是否是同一个 contract coordinate
- 保持条件: logical session/conversation continuity goal
- 改变条件: publisher implementation 与 persistence mechanism
- 预期支持结果: 两家都要求 identifier 之外的 storage/runtime condition 才能建立 durable continuity
- 预期反证结果: 任一当前合同明确把 session identifier 本身定义为 unconditional durable-recovery guarantee

## 原始观测

1. OpenAI current Sessions docs 对 interrupted run 的 resume guidance 同时要求相同 session identity 与相同 underlying storage backend.
2. OpenAI current SQLiteSession reference 明确默认 `:memory:` database 会在 process 结束时丢失，提供 file path 才形成 persistent storage.
3. OpenAI current Sessions docs 还列出 Redis, SQLAlchemy, MongoDB, Dapr 与 server-managed conversations 等不同 storage implementations，说明 session abstraction 与 backend persistence 是分离 coordinate.
4. Google current agents-cli docs 明确 `--session-id` 用于 conversation continuity，但 local session 存在 running server memory 中.
5. Google current agents-cli docs 明确要跨 separate runs resume local session，需要用 `--start-server` 保持 server alive.
6. Google current agents-cli creation/deployment options把 `in_memory`, `cloud_sql`, `agent_platform_sessions` 暴露为不同 session storage types.
7. 本轮没有运行 OpenAI Agents SDK 或 agents-cli，没有生成 process-restart matrix，也没有取得 recovered conversation artifact.

## 反例检查

最强反例是 durable backend 的存在本身: 相同 session ID 配合 file-backed SQLite, Redis, SQL database, managed session service 或其他持久存储，可以成为有效的 state lookup key，并跨 process lifetime 恢复历史.

因此本轮不能写成 `same session ID never supports durability`.

真正被否定的是更窄的 shortcut: `same session ID alone proves durability`.

另一个反例是 Google local background server 被持续保持时，同一 local session 可以跨 separate CLI runs 连续使用. 这并不推翻本轮判断，因为 continuity 此时依赖 server lifetime 这一额外条件，而不是 identifier 单独生效.

当前状态为 PARTIAL.

两个独立 publisher 的 current contracts 都支持:

当前可以得出的最强结论是: session identifier 是 continuity identity 的一部分，但 durability 必须连同 backend/runtime-lifetime contract 与实际 recovery evidence 一起判断.

由于没有 runtime restart experiment，本轮不判断任何具体 production deployment 的恢复可靠性，也不量化 persistence success rate.
