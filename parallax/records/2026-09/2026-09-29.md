## 研究摘要

本日研究一个 Human Collaboration shortcut: human approval 已经完成，是否就足以证明被批准的工作已经执行完成并产生可取回的 terminal result

OpenAI current Agents SDK HITL contract 把 approval decision 与 resumed execution 分成两个阶段，批准 pending tool call 后需要重新运行原始 top-level run，后续还可能再次出现新的 interruptions

MCP Tasks Extension 把 human-in-the-loop approval gate 列为 durable task 的典型场景，并明确 task handle 承载 durable status，客户端仍需查询 progress 并在任务完成后获取 result

因此本轮得到 bounded result: approval completion 是 control decision，不是 execution completion receipt，也不是 terminal result evidence，当前证据足以否定 approval-equals-completion shortcut，但不足以量化真实系统中 approval 后的失败率或完成时延

## 研究问题

human approval decision 是否足以单独证明被批准工作已经完成，还是 approval state, resumed execution, task terminal state 与 result retrieval 必须作为不同 lifecycle coordinates 验证

## 可证伪假设

- 支持条件: 至少两个独立 publisher 的 current contracts 允许 approval 已完成但后续 execution / task 仍需继续推进或查询 terminal result
- 推翻条件: current contracts 保证 approval decision 一旦产生就等价于工作已经成功完成并且 terminal result 已可取得

## 实验设计

### Trial A

- 目的: 测试 approval decision 是否等价于 resumed execution completion
- 保持条件: 同一个 pending tool call 与 approval decision
- 改变条件: approval 已记录对比 original run 已 resume 并继续执行
- 预期支持结果: approval 之后仍需显式 resume，且后续可以再次产生 interruption
- 预期反证结果: approval API 本身直接定义为 terminal execution success

### Trial B

- 目的: 测试 approval gate 是否等价于 durable task terminal state
- 保持条件: 同一个 long-running human-in-the-loop work item
- 改变条件: approval gate resolved 对比 task status reached terminal completion
- 预期支持结果: durable task handle 在 approval 后仍需要 progress/status lifecycle
- 预期反证结果: approval resolution 自动把 task 定义为 completed

### Trial C

- 目的: 测试 task terminal state 与 result retrieval 是否可坍缩为 approval evidence
- 保持条件: 同一个 durable task identity
- 改变条件: approval event 对比 later result retrieval
- 预期支持结果: result 需要在 task ready 后单独取得
- 预期反证结果: approval event 本身包含并保证最终 result

## 原始观测

1. OpenAI current HITL docs 明确说明 tool call 需要 approval 时 run 暂停并产生 interruptions
2. OpenAI current HITL docs 要求对 interruption 执行 approve 或 reject 后，再把 RunState 交回 Runner 以恢复原始 top-level run
3. OpenAI current HITL docs 明确 resumed run 如果出现新的 approval requirement，会再次进入 interruption flow
4. OpenAI current Running agents docs 将 durable execution integrations 用于 long waits, retries, process restarts 与 human-in-the-loop workflows
5. MCP Tasks Extension current overview 将 human-in-the-loop approval gates 列为 durable tasks 的使用场景
6. MCP Tasks Extension current overview 明确 server 返回 durable task handle 后，client 查询 progress，并在 ready 时 retrieve result
7. MCP Tasks Extension current specification draft 明确 Task 是承载 underlying execution state 的 durable state machine，并通过 polling / deferred result retrieval 将 task state 与 final result 分开
8. 本轮没有运行 OpenAI Agents SDK, MCP Tasks implementation 或真实 long-running job，没有取得 approval-to-terminal timing artifact

## 反例检查

最强反例是短工具调用可能在 approval 后立即 resume 并成功完成，此时 approval event 与 completion event 在时间上非常接近

这不推翻本轮判断，因为时间接近不等于 evidence identity 相同，系统仍可以分别记录 decision 与 execution result

另一个反例是某些 orchestration layer 可以在 UI 中把 approve-and-wait 包装成单一用户动作，用户体验上看起来只有一次操作，这也不证明底层 approval, execution, terminal status 与 result receipt 已经成为同一个 contract event

## 暂时结论

当前状态为 PARTIAL

两个独立 publisher 的 current contracts 共同支持

```text
APPROVAL_DECIDED
!= EXECUTION_COMPLETED
!= TASK_TERMINAL
!= RESULT_RETRIEVED
```

当前可以得出的最强结论是: human approval 应被记录为 control decision evidence，长期自主 Agent 仍需单独保存 resumed execution 与 terminal result evidence，不能从 approved 状态推导工作已完成

由于没有 end-to-end runtime，本轮不判断任何具体 production workflow 的完成可靠性，也不量化 approval 后 failure rate 或 latency

## AGI-scale relevance boundary

长期自主 Agent 的 Human Collaboration 需要把人的 decision 与系统的 later execution result 分开记账

如果 approval 被直接当成 completion，long wait, retry, process restart, second approval 与 external job failure 都可能被 evidence layer 隐去

本轮研究的是 human decision 到 durable execution 的 lifecycle boundary，不构成模型能力或 AGI capability 声明
