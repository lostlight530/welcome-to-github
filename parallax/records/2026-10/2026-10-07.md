## 研究摘要

本日测试一个 cancellation shortcut：发送 cancel、收到 cancellation acknowledgement，或观察到本地 cancelled flag，是否已经足以证明底层工作进入 terminal cancelled 并且 run 已 settled

MCP Tasks Extension 2026-07-28 明确把 `tasks/cancel` 成功响应定义为空 acknowledgement，并说明 cancellation processing 是 eventually consistent；ack 之后 task 仍可保持 `working`，甚至最终进入非 `cancelled` terminal status

OpenAI Agents SDK TypeScript current streaming contract 明确说明，主动 abort signal 或取消 stream reader 后，即使 `stream.cancelled` 已为 true，仍必须等待 `stream.completed` 才能把该 run 当作 settled，因为 SDK 可能仍在持久化当前 turn input 或完成 cleanup

A2A Protocol v1.0.1 同样把 Cancel Task 定义为 cancellation attempt，规范明确说明 success is not guaranteed，并返回 updated Task state 或相应错误

因此 cancellation intent、cancellation acknowledgement/flag、terminal cancelled state 与 settled execution 是需要分开的 lifecycle evidence

## 研究问题

跨当前 Agent runtime / protocol contract，cancellation request、acknowledgement 或 cancelled flag 是否足以证明底层执行已经 terminal cancelled 且 lifecycle 已 settled

## 可证伪假设

- 支持条件: 至少一个 current contract 明确允许 cancellation acknowledgement/flag 先于 terminal cancelled 或 settled state，且其他独立 publisher 不把 cancel request 定义为无条件终态
- 推翻条件: current contracts 普遍规定 cancel request/ack/flag 一旦成功出现就同步、不可逆地证明 underlying execution 已 terminal cancelled 且无需进一步 settlement evidence

## 实验设计

### Trial A

- 目的: 测试 MCP cancel acknowledgement 是否等于 terminal cancelled
- 保持条件: same in-progress task identity
- 改变条件: cancel request acknowledged versus later observable task status
- 预期支持结果: ack 可以先于 terminal state，且最终状态不保证为 cancelled
- 预期反证结果: acknowledgement 本身同步返回并保证 terminal cancelled

### Trial B

- 目的: 测试 OpenAI streaming cancelled flag 是否等于 run settled
- 保持条件: same streaming run and same cancellation action
- 改变条件: `stream.cancelled` flag versus `stream.completed` settlement
- 预期支持结果: cancelled flag 出现后仍要求等待 completed
- 预期反证结果: cancelled flag 一出现 SDK contract 即允许把 run 当作 fully settled

### Trial C

- 目的: 测试 A2A Cancel Task request 是否无条件形成 canceled terminal state
- 保持条件: same ongoing task identity
- 改变条件: cancellation attempt versus returned updated task/error
- 预期支持结果: cancellation can fail or be unsupported for current state，必须观察 returned task state/error
- 预期反证结果: valid Cancel Task request 对所有 ongoing tasks 都保证进入 canceled terminal state

## 原始观测

1. MCP `tasks/cancel` 的成功结果是 empty acknowledgement，而不是一个 guaranteed-cancelled Task object
2. MCP 明确允许 cancellation ack 后 observable task status 继续保持 `working` 或其他 non-terminal state
3. MCP 明确允许 underlying work 在 cancellation 生效前完成，因此最终 terminal status 可以不是 `cancelled`
4. MCP 将 cancellation 描述为 cooperative intent，server 决定是否以及何时 honor，eventual cancelled 不保证
5. OpenAI current streaming docs 要求 abort signal 或 reader cancellation 后继续 await `stream.completed`，否则不能把 run 当作 settled
6. OpenAI current streaming docs 明确说明 SDK 可能仍在持久化当前 turn input 或完成 cleanup
7. OpenAI `stream.cancelled` 可以为 true，同时 `stream.finalOutput` 仍可能 undefined，因为当前 turn 没完成
8. A2A v1.0.1 明确说明 Cancel Task success is not guaranteed
9. A2A cancellation operation 返回 updated Task state，并定义 TaskNotCancelableError 处理不可取消状态
10. 本轮没有执行 MCP server、OpenAI Agents SDK stream、A2A agent 或 cancellation wire trace

## 反例检查

最强反例是某个具体 A2A implementation 在收到合法 cancel 后立即返回 `TASK_STATE_CANCELED`，或者某个 OpenAI streaming run 在 cancelled flag 出现时 `stream.completed` 已经同步 resolved

这些路径会让 cancellation event 与 terminal/settled state 在单次执行中非常接近，甚至同一观察时点可同时成立

但它们不推翻本轮，因为本轮否定的是“仅凭 cancellation request/ack/flag 就跨系统推断 terminal cancellation 与 settlement”的充分性；MCP 直接允许 ack 后继续 non-terminal，OpenAI 直接要求 completed settlement evidence，A2A 也不保证 cancel success

另一个反例是 client policy 选择发出 cancel 后立即丢弃 task state。MCP contract 允许 client 不再轮询，但这属于 client retention policy，不等于 server-side terminal cancellation 已被观测证明
