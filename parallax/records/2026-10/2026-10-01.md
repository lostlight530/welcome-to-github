## 研究摘要

本日测试跨 Agent protocol 的一个 status shortcut：看到 terminal `completed` 是否足以把结果解释为同一种 semantic success

A2A current development specification 将 completed 描述为 task successfully completed 的 terminal state。MCP Tasks Extension 则明确规定：底层 method result 即使携带 `isError: true`，也必须使用 `completed`，只有 JSON-RPC execution error 才进入 `failed`

因此相同或相近的 terminal label 不能脱离 protocol-specific result/error contract 直接归一化成统一 semantic-success 指标

## 研究问题

跨协议聚合时，`completed` terminal status 是否足以证明同一层级的 semantic success

## 可证伪假设

支持条件：两个独立 protocol authority 对 completed/failed 与 result-level error 的边界不同。推翻条件：两者都定义 completed 为相同且无 error-bearing result 的 semantic-success contract

## 历史背景

9/29 拆分 approval 与 completion，9/30 拆分 timeout scope。本轮进一步研究 terminal label 自身的语义 identity，避免 observability/evaluation 层把不同 protocol 的 completed 机械归一

## 实验设计

### Trial A
A2A：保持 TaskState surface，比较 completed 与 failed 的 normative meaning

### Trial B
MCP：保持 task terminality，比较 JSON-RPC execution error 与 method-result `isError: true` 的 status mapping

### Trial C
跨协议：保持 `completed` label，测试能否在没有 protocol/result identity 时直接归一为同一个 semantic-success category

## 原始观测

1. A2A completed 是 terminal state，并描述为 task successfully completed
2. A2A failed 是独立 terminal state
3. MCP JSON-RPC execution error 将 task 移到 failed
4. MCP 明确 method-result error 不能使用 failed；例如 tool result `isError: true` 必须保持 completed 并把 error details 放在 result
5. 因此 MCP completed 不能单独证明 result 内不存在 error-bearing method outcome
6. 本轮没有执行 live A2A/MCP task，也没有进行 application-level semantic adjudication
