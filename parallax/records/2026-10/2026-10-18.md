## 研究摘要

本日检验一个可证伪的跨层捷径: workflow 能够 replay、checkpoint 或在调度层只观察到一次完成, 是否足以推断外部 Tool 写操作恰好生效一次

直接核验 Temporal、LangChain、IETF 和 Stripe 四个独立发布者的五份权威材料, 然后在隔离的标准库 synthetic sink 中注入 effect 已提交但 acknowledgement 丢失的窗口, 比较稳定 key、旋转 key、key 过期、参数冲突和跨 workflow key collision

8 个 scenario 和 44 项最终断言执行通过, 总计 11 个模拟 effect、2 次模拟去重和 1 次参数拒绝, 这些数字仅属于本地研究者模型, 不属于真实服务或框架的运行统计

## 研究问题

当 Agent 的 durable workflow 在外部 Tool effect 已发生但 completion acknowledgement 未被持久化时, replay 或 retry 能否仅凭 workflow-level completion、thread ID 或请求重发而保证外部 effect 恰好一次, 哪些额外身份与 receipt 条件能使该判断可验证

## 可证伪假设

- 支持条件: Temporal 明确区分 workflow replay 与 Activity retry, LangGraph 明确描述 node retry/checkpoint 范围, HTTP 规范区分 intended idempotent effect 与其他副作用, Stripe 文档将去重限定于同一 key、参数和保留窗口; synthetic 单变量对照应区分 effect count
- 推翻条件: 对应权威合同明确保证任何没有外部去重机制的 Tool effect 在 acknowledgement-loss 重试后仍只生效一次, 或受控模型中稳定 key 与无 key 在规定 fault window 下无法产生可区分结果
- 限制: 此假设检验的是文档层级的非等价关系与自定义模型, 不是对任何生产服务 exactly-once 实现的合规判断

## 实验设计

### Trial A｜跨发布者 bounded evidence procedure

- 目的: 对照 workflow replay, Activity retry, node attempt retry, HTTP idempotent semantics 和 API-level deduplication 的 authority scope
- 保持条件: 发布者身份、文档对象与版本限定、2026-10-18 access date
- 改变条件: 将 workflow completion、外部 effect、请求去重和业务验收分别作为待验证命题
- 预期支持结果: 四个发布者不会将 replay 或 checkpoint 单独定义为任意外部 Tool effect 的 exactly-once 证明
- 预期反证结果: 存在适用的规范直接把 workflow replay 等价于下游 effect 唯一与客户端验收
- 实际执行: 读取五份官方材料, 未启动相关框架运行时

### Trial B｜acknowledgement-loss synthetic fault injection

- 目的: 在相同模拟 effect 下观察 key identity 与 retention 的变化如何改变 effect count
- 保持条件: Sink 状态机、receipt 格式、同一 payload 和每个 case 的隔离初始状态
- 改变条件: no key、stable key、rotated key、payload mismatch、local TTL expiry、cross-workflow collision、completion checkpoint present
- 预期支持结果: stable key 抑制本地重试重复 effect, no key 和 rotated key 产生重复 effect, key mismatch 被拒绝, expired key 可再次生效
- 预期反证结果: 断言不符合预期, 或在未提供外部 receipt 时误把 workflow checkpoint 当作外部唯一性证明
- 实际执行: 8 scenarios, 每例 5 项断言, 另 4 项聚合断言, 合计 44

## 反例检查

若外部 Tool 服务以稳定的 operation identity 和 payload 约束持久化去重记录, 且记录的保留期覆盖全部重试窗口, workflow 可用相同 operation key 对未知完成状态执行有界重试, 并通过服务端 receipt 与后续业务验收建立更强证据链

该反例反驳的是 workflow replay 本身充分, 不是反驳可靠执行能够通过额外设计达成

另一个负向反例是两个不同业务操作错误复用相同 key, 模型中第二次操作被去重而未生效, 表明减少重复次数也不能自动证明正确的业务语义
