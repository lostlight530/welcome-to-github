## 研究摘要

本轮研究 Agent 跨层重试链中 HTTP `202 Accepted`、服务提供方幂等键与 A2A Task ID 的三种不同身份是否能互相替代, 尤其在原请求响应丢失或重试时能否推断最终外部副作用已发生且获应用方验收

对照 IETF RFC 9110、Stripe Idempotent Requests 和 A2A v1.0.1 路由规范的三个独立发布者, 在本地 Python 3.13.5 标准库确定性 fixture 上执行 15 个 cases 与 51 项断言, 全部通过

结果是自定义 shortcut 仅依据 acknowledgement 在 13 个没有完整 settlement evidence 的 synthetic negative cases 仍为 true, 不说明任何真实 Stripe/A2A 服务重复扣款、误结算或违反规范

## 研究问题

当 HTTP 202 或其他异步确认可见, 且请求具有幂等键或 Agent Task ID 时, 是否足以推出同一 operation 的重放被正确绑定、外部效果恰好一次发生、最终 Task 已完成并获得客户端接受

## 可证伪假设

- 支持条件: HTTP 202 是未完成处理的非承诺确认; Stripe 的 idempotency cache 具有 key、参数及保留窗口边界, 重放的相同响应不自动证明业务成功; A2A Task ID 是服务器生成的对象主键且 Task 具有不同状态, 无跨系统内置等价映射; 单变量 fixture 显示 shortcut 与受限 evidence gate 分歧
- 推翻条件: 适用规范明确要求仅凭 202 或任意幂等键与 Task ID 即可证明独立的最终 effect receipt 和 client acceptance, 或合成实验全部负例与 baseline 无差异
- 适用边界: 研究者定义的 evidence-completeness policy 而非跨 IETF、Stripe、A2A 的共同强制合规门槛

## 反例检查

合法单次业务调用在没有 Stripe-style idempotency key 的情况下也可以最终完成并取得验收凭证, 本研究的 stricter retry_binding gate 对该情形可能 false negative, 因而不能声称该 gate 是 HTTP/A2A 强制规则

即使某个 Stripe key 在有效保存期内稳定返回首个 500 response, 该一致性只表示缓存响应重放, 不证明 operation 或最终业务动作成功

真实系统也可以在收到 202 后异步完成全部工作, 但完成的证据来自之后的 operation/task state、对象级效果与客户端验收, 而不是 202 本身
