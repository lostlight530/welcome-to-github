## 研究摘要

本日测试一个 approval shortcut: 当 human-in-the-loop decision 已经记录为 approve 时, 是否可以直接把该 decision 当成 tool 已通过最终 execution gate 的证据

OpenAI Agents SDK current HITL contract 将需要 approval 的 tool call 记录为 interruption, decision 写入同一 RunState 后再恢复原 run

同一 current contract 明确说明 local function-tool input guardrails 默认在 approval 之后, tool execution 之前运行

如果启用 `preApprovalInputGuardrails`, 同一 input guardrails 可以在 approval request 前先运行一次, 但 approval resolved 后仍会再次运行, 以检查等待期间 call 是否已经变得不安全

因此 approval decision 与 execution-time validation 是两个不同 lifecycle event, approval 本身不能证明 tool execution 已经开始或仍然被允许

## 研究问题

对需要 human approval 的 local function tool, 已记录的 approve decision 是否足以证明该 tool call 已经通过所有 execution-time validation 并进入实际执行

## 可证伪假设

- 支持条件: current contract 在 approval decision 与 tool execution 之间保留独立 input validation stage, 且该 stage 可以 reject 或 throw
- 推翻条件: current contract 规定 approval 一旦记录, tool 必须无条件执行, 中间不存在任何能够阻止执行的 validation gate

## 实验设计

### Trial A

- 目的: 测试 approval decision 是否直接等于 tool execution start
- 保持条件: same local function tool and same pending call
- 改变条件: unresolved approval versus approved state
- 预期支持结果: approve allows run to resume but does not bypass subsequent execution-time guardrails
- 预期反证结果: approval immediately and unconditionally starts the tool before any further validation

### Trial B

- 目的: 测试 post-approval input validation 是否可以独立阻止 execution
- 保持条件: same approved tool call
- 改变条件: input guardrail behavior `allow` versus `rejectContent` / `throwException`
- 预期支持结果: rejected or tripped validation prevents the tool from executing despite prior approval
- 预期反证结果: prior approval forces execution even when the guardrail rejects

### Trial C

- 目的: 测试 pre-approval validation 是否消除 post-approval validation identity
- 保持条件: same tool, same guardrail, `preApprovalInputGuardrails: true`
- 改变条件: validation phase before approval versus repeated validation after approval
- 预期支持结果: guardrail can run before approval and still runs again before execution after approval
- 预期反证结果: enabling pre-approval validation permanently replaces the execution-time validation pass

## 原始观测

1. OpenAI current HITL documentation states that a tool requiring approval does not execute when no approval decision is stored
2. The run records a `RunToolApprovalItem`, pauses, and returns pending approvals through `interruptions`
3. An application records approve or reject on the stored RunState and resumes by passing that updated state back to the original runner
4. By default local function-tool input guardrails run after approval immediately before the tool executes
5. Input tool guardrails can allow, rejectContent or throwException, so the post-approval gate can prevent tool execution
6. With `preApprovalInputGuardrails: true`, a guardrail may also run before the pending approval is shown
7. If that early guardrail allows the call and approval is later granted, the same input guardrails run again before execution
8. No Agents SDK runtime, approval replay trace, tool-side effect marker or exact execution timestamp was captured in this research window

## 反例检查

最强反例是某个具体 tool 没有配置 input guardrails

在这种 harness 中, approval 后可能没有这一个 post-approval validation stage, 因而 approve 与 tool start 可以在局部执行路径上非常接近

该反例不推翻本轮, 因为本轮否定的是把 approval decision 普遍当成 execution-time validation 已完成的充分证据

第二个反例是 guardrail 在 pre-approval 和 post-approval 两次都对同一 immutable input 返回 allow

这时两个 validation event 的结果相同, 但 event identity 仍然不同, 因为它们位于 approval 前后两个 lifecycle cut, 并且 current contract 明确保留第二次 execution-time validation
