## 研究摘要

研究对象是长期 Agent 通过 A2A 完成任务后，后续 refinement 生成同名 artifact 时，客户端能否仅凭相同 contextId、相同 artifact name、较晚 generation order 或 completed task 推断它是原 artifact 的有效新版本，且已经被客户端接受

A2A v1.0.1 specification 区分 Task、Message、Artifact；artifactId 只保证在一个 Task 内唯一，Task history 可选且不保证保留全部消息。A2A v1.0.1 Life of a Task 进一步明确：terminal task 不能重启，refinement 产生新 Task；artifact mutation lineage 不属于 A2A 协议内建保证，client 负责管理版本关系及接受或拒绝新版本。同名 artifact 是建议性的提示，不是强制 derivation edge

W3C PROV-O 明确提供 entity、activity、agent、wasDerivedFrom 和 wasRevisionOf 等可表达 provenance 的关系，但并不意味着 A2A 自动采用 PROV-O。OpenAI Agents SDK Results and state 将 final output、replay history、last agent 和 interrupted run state 分成不同 surfaces；这仅是另一个 SDK 的对照，不可把两个运行时视为同一实现

本轮在本地执行 6 个 synthetic artifact identity 对象和 10 个断言，构造同 context 同名但非派生、已生成却被拒绝、显式派生且被接受、artifactId 跨 Task 重名、无 parent 时 lineage UNKNOWN 等反例。所有断言通过。结论 PARTIAL：对 contract 与 synthetic identity counterexample 有直接证据，尚未验证真实 A2A server/client 的 provenance 和 acceptance persistence

## 研究问题

在 A2A v1.0.1 中，contextId、artifact name、artifactId、Task completed、后发生成时间是否足以推出跨 Task 的 artifact derivation、最新可接受版本以及客户端最终采用结果；如果不足，何种显式 identity 和 acceptance ledger 才能使判断可复核

## 可证伪假设

- 支持条件: A2A 正式合同将 artifactId 唯一性限定在 Task 范围，并明确 client 管理 artifact mutation linkage 与 acceptance；同 context 同名的受控 fixture 可产生非派生、被拒绝及相互竞争的新对象；显式 task/artifact composite identity 与 parent edge 可以区分这些状态
- 推翻条件: A2A v1.0.1 正式合同保证相同 contextId 加相同 artifact name 自动建立唯一 derivation edge，且 completed task 的 artifact 必然等于 client accepted latest revision；或固定 fixture 中所有同名对象都必然具有相同 parent 和 acceptance
- 证据范围: 仅检验可表达性与不能推断的边界，不声称发现真实 A2A SDK 缺陷

### Trial C: local synthetic lineage/acceptance counterexample

- 目的: 构造 same-name、same-context、later-generated 与 accepted revision 的可区分对照
- 保持条件: six immutable Python dataclass objects, fixed generation order and application-defined parent/accepted flags

- 预期支持结果: naive latest-by-name can choose a rejected object; same-name independent accepted artifact lacks derivation; explicit composite identity resolves reference

## 反例检查

最强反例是某个 A2A client application 持久保存严格的 artifact version ledger、显式 taskId/artifactId parent edges、验收者身份和签名/审计记录，且 server/client 的 current state 能在新窗口直接复验。此时跨任务 lineage 和 acceptance 可以被证明，但证明来自额外的 application ledger 和实测证据，不来自同名 artifact 或 contextId 本身

另一个反例是简单串行工作流每次只生成一个同名 artifact 且用户总接受最新版本。此时 naive latest-by-name 与 latest accepted revision 偶然一致，但不能推广到并发 follow-up、拒绝或分支修改

本地 fixture 中 task-D/a4 虽被接受却不是 base 的显式 revision，task-E/a1 虽最后生成却被拒绝，且 a1 跨 task 重用。该对照推翻了把名称、生成顺序、单独 artifactId 当作可靠 lineage/acceptance 证据的 shortcut，但不证明 A2A 生产 SDK 具有该缺陷

应用级 parent edge 本身也可能被伪造或过时；显式记录只是可审计前提，不自动建立 truth。缺失 parent 应保持 UNKNOWN，而不是直接断言不存在任何真实 derivation
