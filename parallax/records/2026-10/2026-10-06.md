## 研究摘要

MCP 2026-07-28 有两种表面都可见为 input-required 的 continuation path

MRTR 在原始 method 未完成时返回 input-required result, client 提供 response 后重试原始 method

Tasks Extension 在 durable task 执行中需要输入时把 task status 置为 input-required, client 通过 tasks/get 读取请求并通过 tasks/update 提交响应

Tasks specification 明确说明这两种机制不同

## 研究问题

同名 input-required 是否足以确定 continuation contract

## 可证伪假设

- 支持条件: 两种机制使用不同 state carrier, identity handle 和 continuation operation
- 推翻条件: current contract 将两者定义为同一 lifecycle event 和同一 continuation path

## Identity boundary

MRTR result identity != durable task status identity

MRTR request state != durable task ID

original-method retry != tasks/update

## 控制条件

保持需要额外 client input 不变, 只改变输入发生在未完成原始 request 还是 durable task execution

不执行 runtime, 不把多个官方页面计成多个独立来源

## 实验设计

### Trial A

- 目的: 比较 state identity
- 保持条件: additional input need
- 改变条件: MRTR result 对比 task status
- 预期支持结果: carrier 不同
- 预期反证结果: 两者使用同一 state field

### Trial B

- 目的: 比较 continuation operation
- 保持条件: response 已取得
- 改变条件: MRTR 对比 task flow
- 预期支持结果: original retry 对比 tasks/update
- 预期反证结果: continuation method 相同

### Trial C

- 目的: 比较 correlation handle
- 保持条件: multi-round association
- 改变条件: request state 对比 task ID
- 预期支持结果: 两种 handle 语义不同
- 预期反证结果: contract 定义为可互换 identity

## 原始观测

1. MRTR 通过 input-required result 暂停原始 method 的完成
2. client 回送 responses 并重试原始 method
3. request state 在 MRTR rounds 间被回送
4. durable task 可进入 input-required status
5. task input requests 通过 tasks/get 暴露
6. task responses 通过 tasks/update 提交
7. Tasks specification 明确区分 task input requests 与 MRTR
8. 本轮没有 runtime wire trace
