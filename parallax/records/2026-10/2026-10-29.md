## 研究摘要

同一已合并 PR #858 的固定 head 与 merge commit 各有四条 completed/success check runs, 但两组不是同一组: head 包含 CodeQL 而没有 deploy, merge commit 包含 deploy 而没有独立 CodeQL check-run 条目, 两者共同的只有三个 Analyze checks

两个 SHA 各有五条 check suites, 其中 render、cursor、hark 三个 app 的 suite 仍显示 queued, 因此四条成功 check runs 不能外推为全部 suite 已完成, 更不能把 merge commit 的后置检查当作合并前审查证据

## 研究问题

When a PR head and its resulting merge commit each show four successful checks, does equal count establish identical check coverage, pre-merge validation or completed check suites

## 可证伪假设

- 支持条件: pinned head and merge SHAs have equal successful check-run counts but unequal check name/app sets, post-merge checks start after the recorded merge time, and some check suites remain queued at the access cut
- 推翻条件: check-run identities and coverage sets match exactly, merge-side checks demonstrably predate merge, or all suites have direct completed evidence
- 归因限制: a GitHub reported success is scoped to its own SHA, app, workflow and run; absence of one named check on one SHA is not evidence of execution failure or absence outside the queried API

## 历史背景

2026-10-21 separated legacy commit statuses, check runs and filtered workflow projections for two other historical PR heads. 2026-10-22 separated merge state from recorded reviews, 2026-10-23 separated recorded PR base from merge-time first parent. ## 反例检查

The three Analyze checks appear in both name sets, a positive overlap control that prevents treating the entire check collection as unrelated. The head-only CodeQL and merge-only deploy directly falsify identical coverage despite equal totals. Three queued suites on both SHAs refute the assertion that four completed checks imply all suites complete. The merge-side check start timestamps follow the recorded merge timestamp, so these specific executions cannot have been completed as a prerequisite before that merge. No evidence establishes why the three app suites remain queued or what policy was in force at merge time

## 暂时结论

PARTIAL: the observed equal count of successful check runs across PR head and merge commit masks a real change in check name and execution identities. Merge-side checks and deploy occurred after the recorded merge, so they cannot be reused as evidence of pre-merge validation. This bounded finding concerns GitHub REST objects for PR #858, not all PRs, historical rulesets, review approval, native Parallax checker PASS or public website semantic acceptance
