## 研究摘要

本日研究一个不同于 10/09 reconnect history 的命题: 配置了 task notification webhook, 或收到了 subscription acknowledged, 是否足以证明后续每个 task update 已被客户端成功接收并完成业务处理

A2A v1.0.1 明确规定配置 webhook 后 agent MUST attempt delivery at least once, failed delivery retry 为 MAY, 连续失败后可以停止尝试; client 以 HTTP 2xx acknowledgement 表达 successful receipt, 且因可能重复投递而 SHOULD idempotent processing. 这些条款没有把已配置、已尝试、已收到 HTTP 2xx 和下游业务落账合并为一个状态

MCP Tasks Extension 2026-07-28 允许 server MAY 发送 notifications/tasks, subscriptions/listen 的 acknowledged notification 返回 server 同意订阅的 task IDs; 每条实际发出的通知包含当时完整 DetailedTask, 但该 acknowledgement 不等于客户端已经收到任何后续 task notification

本轮额外执行 synthetic finite ledger: 保持 task ID、subscriptionAccepted 和 sendAttempted 相同, 令 transport receipt 不同; 再保持 transport 2xx 相同, 令 applicationApplied 不同. 两组可计算反例说明只观察前级标记不能唯一推断后级状态, 不构成真实协议丢包或重复率测量

## 研究问题

在同一 task identity 下, A2A webhook configuration 或 MCP task subscription acknowledgement 是否足以证明 subsequent notification 的 successful receipt、exactly-once processing 与 application-side durable effect

## 可证伪假设

- 支持条件: 正式规范明确将 registration/subscription acknowledgement 与实际通知发送/接收分离, 且至少一个协议明确允许未完成投递或重复投递, bounded synthetic control 存在相同前级状态但不同后级结果
- 推翻条件: 当前适用的正式合同要求配置或 subscription acknowledged 响应本身携带后续每个 notification 的可验证收据和业务提交证明, 或 synthetic 投影在固定条件下必然唯一确定 receipt 与 application outcome

## Identity boundary

```text
WEBHOOK_CONFIGURED_OR_SUBSCRIPTION_ACKNOWLEDGED
!= NOTIFICATION_DELIVERY_ATTEMPTED
!= NOTIFICATION_RECEIVED_AND_ACKNOWLEDGED
!= APPLICATION_EVENT_DURABLY_APPLIED
!= EXACTLY_ONCE_BUSINESS_EFFECT
```

A2A webhook HTTP 2xx 是 transport receipt acknowledgement, MCP subscriptions/listen acknowledged 是 subscription acceptance notification. 它们不属于同一 protocol method 或同一 acknowledgement layer

## 控制条件

固定 logical task ID, 同一 notification consumer 角色, 区分配置/订阅身份、单次投递 attempt、HTTP response、业务落账和任务终态

A2A 固定 v1.0.1 push-notification webhook, 不把 task stream broadcast 或 GetTask polling 的合同替代为 webhook delivery guarantee

MCP 固定 2026-07-28 Tasks Extension, 不把 subscriptions/listen acknowledged 误读为每条后续 notification 的接收回执

Synthetic control 仅改变明确列出的 boolean outcome, 不是 wire protocol simulation; 不引入真实 transport, network retries, storage transaction 或 semantic result

## 实验设计

### Trial A

- 目的: 核验 A2A configured webhook 是否自动证明 successful receipt 与 exactly-once processing
- 保持条件: same task ID, same webhook config, A2A v1.0.1 push delivery
- 改变条件: configured/attempted versus client HTTP 2xx acknowledgement and application commit
- 预期支持结果: at-least-once delivery attempt, optional retries, duplicate possibility and separate client receipt acknowledgement
- 预期反证结果: 规范直接规定 configured response 就是已收到且已持久处理全部通知的证明
- 执行方式: E1 正式规范直接核验, NOT_EXECUTED live webhook

### Trial B

- 目的: 核验 MCP subscription acknowledgement 是否等于 task notification delivery
- 保持条件: same task ID, same MCP Tasks Extension version
- 改变条件: server acknowledged taskId versus an actual notifications/tasks message
- 预期支持结果: acknowledgement 仅列 agreed taskIds, notifications/tasks 由 server MAY push
- 预期反证结果: acknowledged message 本身包含后续所有 task notification 的 receipt or processing evidence
- 执行方式: E2 正式规范直接核验, NOT_EXECUTED live MCP stream

### Trial C

- 目的: 测试 registration/attempt/receipt 的投影能否唯一决定后级业务处理
- 保持条件: synthetic-task-10, subscriptionAccepted=true, sendAttempted=true
- 改变条件: A http2xx=false/applicationApplied=false; B http2xx=true/applicationApplied=true; C http2xx=true/applicationApplied=false
- 预期支持结果: A/B same registration and attempt but different receipt; B/C same receipt but different application
- 预期反证结果: same fixed projection 强制相同的 receipt/application values
- 执行方式: 直接执行 deterministic local JavaScript object comparison, no external runtime

## 原始观测

1. E1: A2A v1.0.1 agent MUST attempt webhook delivery at least once for each configured webhook
2. E1: failed delivery retry 为 MAY, agent MAY 在连续失败达到配置数量后停止尝试
3. E1: client MUST respond HTTP 2xx to acknowledge successful receipt; SHOULD idempotently process because duplicate deliveries may occur
4. E1: client MUST validate expected task ID; webhook authentication/source validation 属于另一控制层, 不自动由 transport 2xx 证明
5. E2: server MAY push notifications/tasks, client 用 subscriptions/listen 申请 taskIds
6. E2: notifications/subscriptions/acknowledged 仅列 server 同意的 taskIds if any, 缺失 extension capability 会触发 JSON-RPC error
7. E2: 单条实际 notification 带 current DetailedTask; 普通 notifications/progress 和 notifications/message 不支持在该 task listen stream
8. Synthetic input A = {taskId:synthetic-task-10, subscriptionAccepted:true, sendAttempted:true, http2xx:false, clientApplied:false}
9. Synthetic input B = {taskId:synthetic-task-10, subscriptionAccepted:true, sendAttempted:true, http2xx:true, clientApplied:true}
10. Synthetic input C = {taskId:synthetic-task-10, subscriptionAccepted:true, sendAttempted:true, http2xx:true, clientApplied:false}
11. Executed predicates: same_subscription_A_B=true; same_attempt_A_B=true; different_http_ack_A_B=true; same_transport_ack_B_C=true; different_application_B_C=true

## 反例检查

最强反例是具体部署实现 durable outbox, receiver inbox, stable event ID, application transaction and replay/ack ledger, 并且把应用提交结果绑定到可验证的回执. 这种 implementation-specific contract 能对指定事件提供比基础规范更强的 end-to-end proof, 但本轮未取得其实际运行证据

另一个反例是 webhook consumer 仅在 durable commit 完成后才返回 2xx. 对该特定 implementation, 已验证的 2xx 可能成为 application settlement 的证据, 但需要先证明 consumer 的 ack-after-commit 合同与实际运行, 不能从 A2A 一般 2xx receipt semantics 推断所有客户端都如此

Synthetic C 刻意让 B/C 同为 HTTP 2xx 但业务效果不同, 证明 ledger 投影不足, 不能当作某个真实 A2A server/consumer 的故障观察

## 暂时结论

当前状态为 PARTIAL

```text
SUBSCRIPTION_ACCEPTED
+ DELIVERY_ATTEMPT
!= PROVEN_RECEIPT
!= PROVEN_APPLICATION_COMMIT
```

A2A v1.0.1 明确只要求至少一次 webhook delivery attempt, retry 不是无条件强制, duplicate deliveries 可能发生. MCP Tasks Extension 的 task subscription acknowledgement 只建立 server agreed task IDs, 不是每个 future notification 的 receipt. 两者均不能单凭前级状态推出 exactly-once business effects

长期 Agent notification ledger 建议分别保存 task identity, subscriber/webhook identity, subscription acknowledgement, notification/event ID, send attempt, HTTP response or stream receipt, consumer deduplication, application transaction and independent reconciliation evidence

## AGI-scale relevance boundary

多 Agent 任务委托、异步回调与长时自动化中, 控制面已经接受订阅不能证明下游执行器已经观察、接受或持久应用关键通知. 需要明确谁对 delivery, receipt, processing 和 durable effects 提供证据

这是 distributed-agent evidence integrity 问题, 不是 AGI capability claim, 也不是 A2A 与 MCP 的真实可靠性优劣测量
