## 研究摘要

本日研究 reconnect 后的一个容易混淆的承诺: 客户端能通过同一 task ID 重新取得当前状态, 是否就能证明断线期间所有 intermediate events、消息和状态转移已被完整恢复

A2A v1.0.1 明确规定 SubscribeToTask 的首个事件是订阅时当前 Task, 并直接警告断线重连后客户端可能错过 status update messages; Task history 不保证保存全部消息, GetTask 的 historyLength 还允许 server 返回比请求更少的消息

MCP Tasks Extension 2026-07-28 提供 durable task handle、tasks/get 当前 DetailedTask 与可选 notifications/tasks; 每个 notification 也是当时的完整当前状态, 而不是一个承诺可重放所有历史事件的 append-only journal

为测试推断是否充分, 本轮执行一个明确标为 synthetic 的确定性对照: 两条不同的 intermediate-message histories 被投影为完全相同的 final state 和 artifact. 这只证明 snapshot projection 本身不具备反演唯一性, 不冒充真实协议丢事件测量

## 研究问题

对于一个断线后可重新读取的 task, same task ID 加 current-state snapshot 是否足以证明中间事件序列与消息历史被 losslessly recovered

## 可证伪假设

- 支持条件: 至少一个当前正式协议明确允许 missed intermediate events 或未持久化消息, 且 bounded control 显示不同 event histories 可以产生相同 current snapshot
- 推翻条件: 适用的正式合同要求同一 task 的恢复操作返回带完整顺序和缺口证明的所有历史事件, 或当前快照携带足以唯一恢复原 event history 的证据

## 实验设计

### Trial A

- 目的: 测试 A2A SubscribeToTask 重连返回当前 Task 是否保证补齐断线期间全部消息
- 保持条件: same task ID, A2A v1.0.1 Task lifecycle stream
- 改变条件: uninterrupted stream versus reconnect after a gap
- 预期支持结果: contract 允许 missed status updates 且 Task.history 不保证保留全部 Messages
- 预期反证结果: spec 强制回放每个 missed status/message, 并提供完整性证明
- 执行方式: 直接读取 E1 的 SubscribeToTask, GetTask 和 Messages and Artifacts 条款; NOT_EXECUTED live disconnect

### Trial B

- 目的: 测试 MCP tasks/get 当前状态是否等价于完整中间事件历史
- 保持条件: same task ID, 2026-07-28 Tasks Extension
- 改变条件: current DetailedTask read versus notification sequence
- 预期支持结果: 当前合同明确提供 snapshot/status, 但没有在所核验条款中定义 lossless replay journal
- 预期反证结果: 同一规范要求 tasks/get 返回完整有序历史事件及 gap-free replay guarantee
- 执行方式: 直接读取 E2; 结论限于 documented contract scope, NOT_EXECUTED MCP server

### Trial C

- 目的: 测试仅凭 terminal state/artifact 是否能唯一反推出 intermediate-message history
- 保持条件: same synthetic task ID, submitted/working/completed state shape, identical terminal artifact report-v1
- 改变条件: working event 的 message 从 progress alpha 改为 progress beta
- 预期支持结果: 两条 histories 不同, terminal snapshot projection 相同
- 预期反证结果: 在相同投影定义下两个 final snapshots 不相同
- 执行方式: 本轮直接执行 deterministic local JavaScript finite-sequence comparison, 不依赖网络

## 原始观测

1. E1: SubscribeToTask MUST 返回订阅时当前 Task 作为第一个 event, 这解决的是订阅起点 current state, 不自动提供之前所有 intermediate events
2. E1: v1.0.1 明确指出 streaming client 断线重连后 MAY miss status update messages
3. E1: not all Messages guaranteed persisted in Task history, 包括 transient informational messages 与 task 创建前的消息
4. E1: agent MAY 选择持久化重要消息, 但 client MUST NOT 在没有 out-of-band negotiation 时依赖该行为
5. E1: GetTask 的 historyLength 限制请求的最近消息数, server MAY 返回更少
6. E2: tasks/get 返回 current task status/result, notifications/tasks 每条包含与当时 tasks/get 相同的 DetailedTask
7. E2: notifications/tasks 是 MAY 的可选推送机制, 所核验的条款没有声明断线区间所有 notification 的 gap-free replay
8. Synthetic local execution: H1 = [submitted:accepted, working:progress alpha, completed:done/report-v1]
9. Synthetic local execution: H2 = [submitted:accepted, working:progress beta, completed:done/report-v1]
10. Synthetic local execution: JSON(H1) != JSON(H2) 为 true, JSON(project(H1)) == JSON(project(H2)) 为 true; projection 仅取 final state=completed 与 artifact=report-v1
11. 本轮没有真实 A2A/MCP task ID、wire trace、reconnect timestamps、server event journal 或丢失事件计数

## 反例检查

最强的系统级反例是 server 明确实现 durable append-only event journal, 为每个 task 提供 monotonic sequence ID、acknowledged cursor 和 gap-detection/replay, 客户端在断线重连后成功补齐所有遗漏事件

这个实现完全可能, 但 E1 的默认 Task.history 和 SubscribeToTask contract 不把它作为普遍保证; E2 的 tasks/get 当前状态也不能替代这种额外 replay evidence. 若获得这样的真实 journal 与 wire trace, 应对该具体 implementation 重新判断

另一个反例是某个 task 只有 initial 与 terminal events, 没有任何 intermediate messages; 此时当前 snapshot 可能已经覆盖全部业务所需状态. 这不证明一般情形下历史完整, 也不反驳存在两条不同 intermediate histories 产生相同 snapshot 的控制结果

Synthetic Trial C 的边界是刻意投影丢弃中间消息, 因而只能证明信息不可逆的结构可能性, 不能证明协议实现实际删除了数据

当前状态为 PARTIAL


A2A v1.0.1 对断线后 missed status messages 和不完整 Task.history 提供直接规范级支持. MCP Tasks Extension 对 durable current-state recovery 提供独立结构对照, 但是否有 server-specific replay 扩展或真实事件损失保持 UNKNOWN
