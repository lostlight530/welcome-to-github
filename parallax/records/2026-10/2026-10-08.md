## 研究摘要

本日测试一个 observability shortcut：已经收到 progress/task notification、stream event 或可见 partial output，是否足以证明底层 Agent/task 已完成并且 final result 已经可安全消费

MCP Tasks Extension 2026-07-28 把 task 定义为 durable state machine；task notification 携带当时完整 DetailedTask，客户端仍以 task status 和 final result/error 区分 working/input_required 与 completed/failed/cancelled。规范同时明确 task subscription 不承载普通 progress/message notification，因此“观察到活动”与“取得 terminal task result”不是同一 evidence surface

OpenAI Agents SDK current streaming contract则明确：stream event 用于观察运行过程；必须持续消费 `stream_events()` 直到异步迭代结束，之后 streaming run 才算完成，`final_output` 在 run 完成前保持 None，且最后一个可见 token 之后仍可能有 session persistence、approval bookkeeping 或 history compaction

因此 intermediate observability、terminal lifecycle 与 final-result availability 需要分开记录

## 研究问题

跨当前 Agent runtime / protocol contract，收到 progress/task notification、stream event 或 partial output 是否足以证明 underlying execution 已 terminal complete 且 final result 已稳定可用

## 可证伪假设

- 支持条件: 至少两个独立 publisher 的 current contract 明确把 intermediate event/notification 与 terminal completion/final result 分离
- 推翻条件: current contracts 普遍规定任一可见 progress/stream event 一旦出现就同步、不可逆地证明 execution terminal 且 final result 已完整可用

## 实验设计

### Trial A

- 目的: 测试 MCP task notification / observable task state 是否等于 terminal result
- 保持条件: same task identity
- 改变条件: observed DetailedTask status versus terminal status plus result/error
- 预期支持结果: working/input_required observation 不足以证明 terminal/final
- 预期反证结果: 任一 task notification 均只会在 terminal result 已确定后出现

### Trial B

- 目的: 测试 OpenAI stream event / visible token 是否等于 run completion
- 保持条件: same streaming run
- 改变条件: event/token arrival versus stream iterator exhaustion
- 预期支持结果: events 可在 run completion 前持续出现
- 预期反证结果: 第一个或最后一个 visible event 本身被 contract 定义为 completed run

### Trial C

- 目的: 测试 final_output availability 是否可由 intermediate stream observation替代
- 保持条件: same RunResultStreaming
- 改变条件: stream in progress versus finished
- 预期支持结果: final_output 在完成前保持 None
- 预期反证结果: final_output 在任意 intermediate event 后即保证稳定可用

## 原始观测

1. MCP Tasks extension 将 task 描述为 carrying underlying execution state 的 durable state machine
2. MCP task notification 携带 notification 时刻完整 DetailedTask，与当时 tasks/get 可返回的状态一致
3. MCP task status 明确区分 working、input_required、completed、failed、cancelled；completed/failed/cancelled 才是 terminal
4. MCP task subscription 明确不支持普通 notifications/progress 与 notifications/message
5. OpenAI streaming docs 明确要求持续消费 stream_events 直到 async iterator 结束，之后 streaming run 才算 complete
6. OpenAI docs 明确最后一个 visible token 后仍可能发生 session persistence、approval bookkeeping 或 history compaction
7. OpenAI Results 文档明确 final_output 在 streaming run 完成前保持 None
8. 本轮没有执行 MCP task、OpenAI Agents SDK streaming runtime、wire capture 或 event-loss/reconnect experiment

## 反例检查

最强反例是某个短任务只产生一个事件，而且该事件与 terminal result 在同一时刻可见；这会让 event 与 completion 在该次运行中时间上重合

但它不推翻本轮充分性判断，因为规范仍没有把“任意 intermediate event”定义为 terminal proof；OpenAI 直接以 iterator exhaustion/final_output availability 建立完成边界，MCP 直接以 task status/result 建立 terminal boundary

另一个反例是 UI 只订阅 terminal task notification；此时“收到该 notification”可以同时携带 terminal state 和 result，但证明力来自 notification 内的 terminal status/result，而不是来自“notification 出现”这一事实本身
