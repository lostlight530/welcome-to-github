## 研究摘要

研究构建产物 Attestation metadata 是否能够直接证明某个 Agent deployment 具有被独立验证的构建来源、获准部署并最终完成业务验收

本轮核验 5 份官方材料, 来源按 GitHub、in-toto、SLSA、Sigstore 计为 4 个发布者身份, SLSA 两个 URL 不增加独立发布者数

本地 Python 3.13.5 对受控对象执行 13 个 synthetic cases 和 57 项断言, 结果全部符合预先定义的期望, 12 个 metadata-present 负例均没有获得最终 runtime_accepted 判定

结果仅证明自定义 gate 可以显式保持 identity 和 state 的分层, 不声称真实代码签名、准入控制或 Agent Runtime 已获验证

## 研究问题

存在一份声称对应 artifact 的 Attestation metadata, 是否充分证明其主体 digest、预期签名身份、构建器与来源策略均被验证, 以及相同 digest 的部署准入、运行和客户端语义验收已真实发生

## 反例检查

若部署方真实核验了相同 subject digest 的签名、证书与 signer-builder policy, 部署控制器对相同 digest 产生独立准入决策, 且实际运行具备可关联的 run ID、结果摘要和客户端 acceptance receipt, 可以构造端到端证据链

该反例表明问题不是 Attestation 完全无用, 而是 Attestation 本身只覆盖链上的特定层, 验签、准入和业务结果均需要不同主体的附加证据

协议自身可能允许其他工作流的消费策略; synthetic gate 中的 runtime acceptance 要求是本研究的更严格问题条件, 不是 in-toto/SLSA/Sigstore 普遍强制要求
