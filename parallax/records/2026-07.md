# 观察记录 2026-07

## 2026-07-20

### 研究问题

固定证据层级能否阻止把官方声明扩大成未经验证的运行结论.

### 证据

- [OpenAI Agents SDK Tracing](https://openai.github.io/openai-agents-python/tracing/), 官方技术文档, 访问日期 2026-07-20.
- [OpenAI Agents SDK Guardrails](https://openai.github.io/openai-agents-python/guardrails/), 官方技术文档, 访问日期 2026-07-20.
- [Hermes Agent Scheduled Tasks](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron/), 官方技术文档, 访问日期 2026-07-20.
- [OpenClaw AGENTS.md](https://github.com/openclaw/openclaw/blob/main/AGENTS.md), 官方源码仓库规则, 访问日期 2026-07-20.
- [openJiuwen](https://openjiuwen.com/en/), 官方产品与技术说明, 访问日期 2026-07-20.

### 假设

如果先标注证据层级，再形成判断，产品声明将只能产生待验证问题，不能直接升级为已实现能力或比较优势.

### 控制条件

- 只使用公开一手来源.
- 不使用项目热度、第三方评价和宣传排名.
- 每个判断必须能够回指到具体来源.

### 实验

1. 从五个来源提取追踪、护栏、会话隔离、维护边界与状态恢复相关陈述.
2. 按可运行结果、源码契约、技术文档和产品声明分级.
3. 尝试形成跨项目共同结论.
4. 删除无法由当前证据直接支持的扩大解释.

### 原始观测

- OpenAI 文档明确描述运行事件追踪和输入输出护栏，同时提示追踪可能包含敏感数据.
- Hermes 文档明确描述定时任务使用新会话、自包含提示、执行记录和防重入锁.
- OpenClaw 仓库规则明确要求依赖行为以官方文档、源码、类型和实时验证为依据.
- openJiuwen 官方页面声明状态持久化、中断恢复和全链路追踪能力，但本次没有独立运行证据验证这些声明.
- 证据分级阻止了把功能声明扩大为稳定性已经得到证明的结论.

### 反例

- 官方文档可能落后于当前实现.
- 官方源码规则说明维护要求，不等于所有运行都满足要求.
- 产品页面中的能力声明需要源码、测试或运行结果继续验证.

### 暂时结论

状态为观察. 证据分级在本次样本中阻止了一次明显的扩大解释，但单次记录不能证明它能够稳定减少错误判断.

### 复验条件

使用不同项目和不同来源顺序重复 P-02，并记录结论是否保持一致.

### 指标

- 一手来源覆盖 5/5.
- 无依据扩大解释保留 0 项.
- 降级为待验证声明 1 项.
- 长期发现 0 项.
- 有效耗时尚未形成跨时基线.

## 2026-07-21

### 研究问题

当两个当前官方页面对可同时生效的保护数量给出表面相反的描述时, 调换来源顺序是否会改变判断边界, 以及关键机制缺失时是否会拒绝无条件的是或否.

### 证据

- [GitHub About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), 官方技术文档, 访问日期 2026-07-21.
- [GitHub About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets), 官方技术文档, 访问日期 2026-07-21.
- 使用 Python 标准库在线读取两个页面, 均返回 HTTP 200, 并分别找到关于单个经典分支保护规则和多个规则集同时适用的目标陈述.

### 假设

如果判断由证据适用范围而不是出现顺序决定, 两种来源顺序都应区分经典分支保护规则与规则集. 当问题没有说明使用哪种机制时, 判断应拒绝给出无条件的是或否.

### 控制条件

- 问题、两个来源、评估字段和同一会话保持不变.
- 只改变两个来源的出现顺序.
- 评估字段固定为证据覆盖、机制区分、判断边界、缺失条件和复验请求.
- 不读取目标仓库的实际保护配置.

### 实验

1. 在线读取两个 GitHub 官方页面并确认目标陈述仍然存在.
2. 先按经典分支保护规则、规则集的顺序形成一次判断.
3. 再按规则集、经典分支保护规则的顺序形成一次判断.
4. 比较五个固定评估字段, 并检查是否出现无依据的统一结论.

### 原始观测

- 两种顺序都把经典分支保护规则与规则集分开处理.
- 两种顺序都记录经典分支保护规则一次只能应用一个, 多个规则集可以同时应用并聚合, 规则集还可以与经典保护规则叠加.
- 两种顺序都在机制未说明时拒绝无条件回答, 并要求查看具体仓库使用的保护类型与匹配配置.
- 五个评估字段在两次判断中相同, 没有观察到由来源顺序造成的边界变化.

### 反例

- 两次判断发生在同一会话和同一时间窗口, 不能视为跨时独立重复.
- 两个页面来自同一发布者且证据层级相同, 不能代表证据强度不同或发布者相互冲突的情况.
- 固定评估字段可能提高了约束保持, 不能据此推断没有显式字段时也会稳定拒绝.

### 暂时结论

状态为观察. 本次没有发现来源顺序改变判断边界, 并观察到关键机制缺失时的合理拒绝. 这不是候选或长期发现.

### 复验条件

在新的时间窗口和干净会话中重复顺序交换, 再加入一个明确的仓库配置样本. 至少三个独立实验完成反例检查前, 不升级结论.

### 指标

- 一手来源覆盖 2/2, HTTP 状态与目标陈述均已在线验证.
- 约束保持 5/5 个评估字段.
- 重复判断一致性 5/5 个评估字段.
- 无依据声明 0 项.
- 合理拒绝 2/2 次.
- 纠错保持未测试.
- 判断漂移 0/5 个评估字段, 仅限同一时间窗口.
- 人工复核负担为两个来源和五个字段的对照.
- 可计量的在线验证耗时为 9.2 秒, 总有效耗时尚未形成基线.
