## 研究摘要

本批次使用 Atlassian Forge 与 OAuth 2.0 3LO scopes 的官方时间链复验 P-04

2022-02-22 Atlassian 宣布新 scopes 可用并要求迁移

2022-04-20 Atlassian 明确暂停旧 scopes 的 deprecation, 移除 2022-08-23 前完成迁移的要求, 并允许 Forge 或 3LO app 继续使用 classic 或 new scopes

2026-08-21 当前 Jira Cloud platform 文档又明确建议在可用时优先使用 classic scopes, granular scopes 只在不能使用 classic scopes 时使用

这条时间链表明较新有效契约可以改变当前判断, 但不能把 2022 年曾经存在的迁移要求改写成从未发布

本记录是 2026-08-22 的真实后续补录, 不伪装为 2026-08-21 当日执行

## 研究问题

当同一 Atlassian scope 迁移对象经历新 scopes 发布与迁移要求, 后续暂停 deprecation 并取消 deadline, 再到当前文档推荐 classic scopes 时, 判断能否按照可排序官方时间更新当前契约同时保留历史阶段

删除时间或稳定对象身份后, 是否会拒绝把不同阶段拼接成无时间边界的单一规则

## 可证伪假设

- 支持条件: 2022-02-22 的迁移要求保留为历史契约, 2022-04-20 的暂停与 deadline 移除更新其后判断, 2026 当前 Jira 文档进一步限定当前 scope 选择建议, 删除时间或对象身份时判断收窄
- 推翻条件: 因当前 classic recommendation 而声称 2022 迁移要求从未存在, 或因 2022 deadline 曾存在而声称 2026 当前仍必须迁移到 granular scopes, 或删除时间后仍形成确定先后链

## 历史背景

P-04 研究旧契约与更新后的官方契约在明确生效时间下如何更新当前判断并保留历史原因

2026-08-11 使用 Kubernetes deprecated API 链

2026-08-12 使用 Python distutils deprecated 到 removed

2026-08-14 使用 OpenAI GPT-4o 明确 rollback

CASES.md 因此要求后续优先选择 superseded 后恢复, 双向切换或多阶段 replacement, 避免机械重复简单 deprecation 或单次 rollback

Atlassian scopes 时间链同时包含发布要求, 后续 deprecation pause, deadline removal 与多年后的当前推荐, 满足更复杂的多阶段条件
