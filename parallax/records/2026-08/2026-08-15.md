## 研究问题

GitHub 官方可用性报告同时给出 GitHub Pages 事故的平均错误率, 峰值错误率与近似失败请求数

当比例与近似计数同时存在时, 判断能否更新影响边界, 同时拒绝把近似统计反推成精确总请求量, 明确成功率或全部 GitHub 的影响比例

## 可证伪假设

- 完整证据下, 可以描述 GitHub Pages 在固定事故窗口内的平均与峰值错误率以及近似失败请求数
- 删除错误率后, 近似失败请求数不能单独给出请求总体中的失败比例
- 删除失败请求数后, 错误率不能单独给出绝对失败请求数
- 删除服务身份后, 数值不能被扩大为全部 GitHub 流量或全部用户
- 加入精确总请求量与全平台成功率摘要时, 应拒绝把近似计数与平均错误率机械转换为官方已验证的精确分母
- 如果任一关键条件缺失后仍补出精确分母或全平台量词, 则本轮假设失败

## 原始观测

GitHub 2026-05-14 发布的 2026 年 4 月可用性报告记录

- 2026-04-13 18:53 至 20:30 UTC, GitHub Pages 出现错误率升高
- 平均错误率为 10.58%
- 峰值错误率为 12.77% of requests to the service
- 约 1750 万失败请求返回 HTTP 500
- 服务在 20:30 UTC 恢复正常, 事件在 20:35 UTC 完全解决
- 根因说明为自动 DNS 管理工具错误删除 GitHub Pages 后端存储主机的 DNS 记录

本轮直接读取的报告没有给出该窗口的精确总请求数, 没有给出明确成功率字段, 没有给出受影响用户数量

## 控制条件

- 固定对象为 GitHub Pages 服务
- 固定事故窗口为 2026-04-13 18:53 至 20:30 UTC
- 固定平均错误率与峰值错误率为不同统计量
- 保留约 1750 万中的近似性质
- 不把请求数量替换为用户数量
- 不把 GitHub Pages 自动扩大为 GitHub 全平台
- 不把本轮推导值写成 GitHub 原始观测

- 反例: 即使机械相除得到约 1.654 亿请求量级, 该计算仍属于推断, 不能改写为官方原始分母

## 反例与边界

- 平均错误率不能替代峰值错误率, 峰值也不能替代平均值
- 约 1750 万不能改写为精确失败请求数
- 近似失败数与平均错误率不能证明一个官方发布的精确总请求分母
- GitHub Pages 请求统计不能扩大为全部 GitHub 流量
- HTTP 500 请求数量不能替代受影响用户数量
- 事故后复盘报告不等于本轮取得真实生产请求响应
- 同一 GitHub 月报中的多个事故不构成多个独立发布者
