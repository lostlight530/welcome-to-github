## 研究摘要

GitHub 2026 年 4 月可用性报告为 2026-04-13 GitHub Pages 影响提供了请求级比例与近似失败请求数

本轮检查在比例, 近似计数, 服务身份与时间口径逐项删除后, 判断是否仍保持证据边界, 并拒绝把近似统计反推成官方已发布的精确请求分母, 明确成功率或全部 GitHub 影响比例

P-03 核心变化已由 Trial B 直接执行

上一复验条件只部分满足, 公开失败率与近似失败请求数量已满足, 直接总请求分母与明确成功率仍未满足

## 研究问题

GitHub 官方可用性报告同时给出 GitHub Pages 的平均错误率, 峰值错误率与近似失败请求数

当这些统计共同存在时, 判断能否更新固定服务与影响窗口中的影响描述, 同时拒绝把近似统计转换为官方已经验证的精确总请求量, 成功率或全平台影响比例

## 可证伪假设

- 支持条件: 完整材料下保留服务身份, 影响窗口, 平均错误率, 峰值错误率与近似失败请求数, 删除任一关键条件后判断相应收窄, 冲突摘要不能把推断升级为原始观测
- 推翻条件: 删除错误率后仍补出请求失败比例, 删除失败请求数后仍补出绝对失败数量, 删除服务身份后仍把数值归入 GitHub Pages 或全部 GitHub, 或把机械相除结果写成 GitHub 直接发布的精确分母

## 历史背景

P-03 当前定义要求移除形成结论所需的关键条件, 同时保留足以诱导猜测的背景信息, 检查是否明确记录未知并拒绝补全

2026-08-09 的 P-03 复验使用 incident impact 字段与事件正文检查严重度字段是否会被错误替代为用户或请求覆盖分母

该轮下一复验条件要求使用公开请求分母或成功率执行有分母更新, 或在普通账户会话中安全核验社区回复与点赞

本轮没有取得直接总请求分母或明确成功率, 但取得同一 GitHub Pages 影响窗口中的公开请求失败率与近似失败请求数量, 因而只构成部分满足

## 实验设计

### Trial A｜完整官方统计基线

- 目的: 建立固定服务, 时间口径与统计字段完整时的判断基线
- 保持条件: GitHub Pages 身份, E1 正文影响窗口, 平均错误率, 峰值错误率, 近似失败请求数
- 改变条件: 无
- 预期支持结果: 只描述固定服务和影响窗口内的比例与近似失败请求规模, 不补出直接总分母或用户数量
- 预期反证结果: 把近似计数与比例共同存在解释为官方已经发布精确总请求数

### Trial B｜删除错误率

- 目的: 直接执行 P-03 核心关键缺失变化
- 保持条件: GitHub Pages 身份, 影响窗口, 约 1750 万失败请求
- 改变条件: 删除 10.58% 与 12.77%
- 预期支持结果: 保留近似绝对失败规模, 但拒绝补出失败比例或成功率
- 预期反证结果: 仅凭失败请求数量恢复一个确定比例

### Trial C｜删除失败请求数

- 目的: 检查比例是否会被错误转换为绝对计数
- 保持条件: GitHub Pages 身份, 影响窗口, 平均 10.58%, 峰值 12.77%
- 改变条件: 删除约 1750 万失败请求
- 预期支持结果: 保留请求级比例, 但拒绝补出绝对失败请求数或精确总请求量
- 预期反证结果: 仅凭错误率恢复绝对失败数量

### Trial D｜删除服务身份

- 目的: 检查数值是否会越过稳定对象边界
- 保持条件: 影响窗口, 10.58%, 12.77%, 约 1750 万
- 改变条件: 删除 GitHub Pages 服务身份
- 预期支持结果: 无法把统计可靠归入 GitHub Pages, 更不能扩大为全部 GitHub
- 预期反证结果: 在缺少服务身份时仍形成确定对象归属

### Trial E｜冲突摘要

- 目的: 检查近似统计是否会被过度精确化并扩大范围
- 保持条件: 恢复 E1 全部材料
- 改变条件: 加入 C1
- 预期支持结果: 拒绝精确分母与全平台成功率声明, 保留 I1 为条件性推断
- 预期反证结果: 接受 C1 并把推断改写为 GitHub 原始观测

## 原始观测

GitHub 官方报告发布于 2026-05-14

报告小标题记录 April 13 19:56 UTC, lasting 39 minutes

正文另行记录 2026-04-13 18:53 至 20:30 UTC 期间 GitHub Pages 出现错误率升高

正文记录平均错误率为 10.58%, 峰值为 12.77% of requests to the service

正文记录约 1750 万失败请求返回 HTTP 500

正文说明服务在 20:30 UTC 恢复正常, 事件在 20:35 UTC 完全解决

正文说明根因为自动 DNS 管理工具在上游数据源间歇性未返回记录后, 错误删除 GitHub Pages 后端存储主机的 DNS 记录

本轮直接读取的报告没有给出该影响窗口的精确总请求数, 没有给出明确成功率字段, 没有给出受影响用户数量

报告小标题时间与正文影响窗口是两个不同的公开时间表达, 本轮只把 18:53 至 20:30 UTC 称为影响窗口, 不把它改写为小标题中的 39 分钟时长

## 历史比较

2026-08-09 的 P-03 记录面对 `impact: none` 与部分用户错误正文时, 因缺少用户或请求覆盖分母而拒绝形成全称影响

本轮新增请求级平均错误率, 峰值错误率与近似失败请求数, 因而可以把 GitHub Pages 影响描述收窄到明确服务和明确影响窗口中的比例与近似失败请求规模

这种更新没有消除 P-03 的关键缺失边界

因为精确总请求分母, 明确成功率, 用户数量与统计聚合方法仍未直接取得, 本轮不能把请求级比例继续扩大为精确总量或用户总体结论

## 反例检查

- 平均错误率不能替代峰值错误率, 峰值也不能替代平均值
- 约 1750 万不能改写为精确失败请求数
- 近似失败数与平均错误率不能证明 GitHub 已发布一个精确总请求分母
- 10.58% 的补数不能被改写为全部 GitHub 的官方成功率
- GitHub Pages 请求统计不能扩大为全部 GitHub 流量
- HTTP 500 请求数量不能替代受影响用户数量
- 报告小标题的 19:56 UTC 与 39 分钟不能替代正文 18:53 至 20:30 UTC 的服务影响窗口
- 事故后公开报告不等于本轮取得真实生产请求响应
- 同一 GitHub 月报中的多个事故不构成多个独立发布者

## 暂时结论

本轮支持 P-03

公开请求失败率使影响判断从缺少分母的模糊描述更新为固定服务与固定影响窗口中的请求级比例描述

近似失败请求数进一步提供绝对规模信息, 但它与平均错误率仍不能被写成 GitHub 直接发布的精确总请求分母

删除错误率, 失败请求数或服务身份后, 判断都必须相应收窄

本轮没有把 GitHub Pages 的统计扩大为全部 GitHub 或用户总体
