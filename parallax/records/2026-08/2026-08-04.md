## 研究摘要

本专题使用 Crossref REST API 复验 HTTP 错误状态能否单独支持具体原因

`rows=1` 请求返回 HTTP 200

`rows=1001` 请求返回 HTTP 400, 响应正文明确指出 1001 必须是小于或等于 1000 的正整数

Crossref 官方文档写明每页最多返回 1000 项, RFC 9110 只把 400 定义为服务器因感知到的客户端错误而不能或不愿处理请求

只有 400 状态时, 判断保持具体原因未知

加入请求参数与 Crossref 文档后, 可以确认请求违反公开上限, 但直接响应原因仍以响应正文为准

加入响应正文后, 可以把本次 400 归因为 rows 参数校验失败

来源逆序没有改变边界, API 密钥过期摘要被官方公共访问规则与响应正文反驳

## 研究问题

非 GitHub API 的 HTTP 400 是否可以单独证明一个具体失败原因

请求参数, 官方限制文档与响应正文分别能够把归因推进到什么层级

来源顺序和误导性 API 密钥摘要是否改变判断边界

## 可证伪假设

- 支持条件: 只有 400 时拒绝具体归因, 加入参数和官方上限后只确认契约违反, 加入响应正文后才确认本次校验原因, 逆序与误导摘要不改变边界
- 推翻条件: 从 400 单独补出 rows 上限, 忽略正文而采用 API 密钥摘要, 或因来源顺序改变当前原因

## 历史比较

三个 GitHub 历史批次使用保护机制与 HTTP 404

只有 404 时, 判断没有从多种允许原因中选择一个默认原因

本次改用 Crossref 公共 API 与 HTTP 400, 只有状态码时仍保持具体原因未知

本次新增直接响应正文, 使具体原因能够由未验证更新为 rows 校验失败

判断变化由新增直接证据解释, 不是来源顺序或措辞变化

N-01 没有触发失效, 适用边界可以增加 Crossref rows 参数校验与 HTTP 400

## 反例检查

- R2 正文证明在直接诊断存在时可以形成具体原因, 反驳所有 HTTP 错误都必须保持未知
- E2 与 rows=1001 支持参数契约违反, 但文档本身不能替代当前响应正文
- E3 只描述 Crossref 公共访问, 不能证明所有付费访问都没有凭据错误
- R1 的成功请求不能证明 Crossref 所有接口当前正常
- R2 的单个 400 不能证明所有 HTTP 400 都由 rows 参数造成
- RFC 示例不是完整原因清单, 不能从通用定义补出具体业务规则

反例成立并限制扩展范围

## 暂时结论

本批次形成 P-02 的第四次观察与 N-01 失效检查

在 Crossref rows 参数场景中, HTTP 400 单独不足以支持具体失败原因

请求参数与官方上限支持契约违反, 直接响应正文进一步支持本次 rows 校验原因

来源逆序与 API 密钥误导摘要没有改变边界

N-01 保持有效, 适用边界增加本次 Crossref HTTP 400 场景

本次没有证明该结论适用于所有 HTTP 400, 所有 API 或所有执行主体
