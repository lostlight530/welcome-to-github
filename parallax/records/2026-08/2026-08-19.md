## 研究摘要

本批次使用 Cloudflare 2025-12-05 事故复盘作为 GitHub 之外的第二个独立发布者, 检查公开材料直接给出百分比的请求总体身份后, 判断能否进行有边界量化, 并在删除分母身份后重新收窄

结果显示, 原始复盘把受影响客户对应范围写为约占 Cloudflare 所服务全部 HTTP 流量的 28%, 因而可以保存该事故窗口内的比例判断, 但不能从百分比补出请求总数或失败请求数

删除 `all HTTP traffic served by Cloudflare` 后, 单独的 28% 不再具有可核验请求分母, 判断收窄为比例对象未知

同一发布者后续韧性总结使用 `28% of applications behind our network` 描述该事故, 说明应用占比与 HTTP 流量占比属于不同聚合对象, 不能仅因数值相同就互换分母

## 研究问题

第二个独立发布者直接给出请求比例及其总体身份时, P-03 在 GitHub 之外是否仍能允许有边界量化, 同时拒绝在分母身份缺失或聚合对象变化时机械补全

## 可证伪假设

- 支持条件: 保留请求总体身份时接受公开比例, 删除总体身份时把比例对象降为未知, 面对相同数值但不同聚合对象时拒绝互换
- 推翻条件: 删除请求总体身份后仍把 28% 无条件解释为全部 HTTP 流量, 或把应用占比直接当作请求占比, 或从比例自行补出未公开的精确请求计数

## 历史背景

P-03 在 2026-08-18 已通过 GitHub 事故报告取得 1700 万 Git proxy requests 的直接数值分母, 并验证直接分母出现后可以有边界更新

CASES.md 的下一复验条件要求优先使用第二个独立发布者的公开直接请求分母检查可迁移性

本批次改用 Cloudflare 官方事故复盘, 发布者与 GitHub 独立, 统计对象也从 Git proxy 请求切换为 Cloudflare 所服务 HTTP 流量

## 控制条件

- 固定事故为 Cloudflare 2025-12-05 outage
- 固定公开数值为约 28%
- 不把百分比转换为未公开的请求总计数
- 不把 applications 与 HTTP traffic 视为同一统计单位
- 每个 Trial 只改变一个关键证据条件或加入一个明确冲突摘要

## 实验设计

### Trial A

- 目的: 建立第二发布者完整基线
- 保持条件: 事故身份, 时间窗口, 28%, `all HTTP traffic served by Cloudflare`
- 改变条件: 相对前序 GitHub 批次更换为 Cloudflare 官方材料
- 预期支持结果: 接受事故窗口内约 28% 的 HTTP 流量范围, 不补出精确请求数
- 预期反证结果: 因发布者变化而拒绝所有量化, 或自行生成请求总数

### Trial B

- 目的: 直接执行 P-03 核心变化
- 保持条件: Cloudflare 事故身份, 时间窗口, 28%
- 改变条件: 删除 `all HTTP traffic served by Cloudflare` 请求总体身份
- 预期支持结果: 记录 28% 的分母对象未知, 拒绝补成全部 HTTP 流量
- 预期反证结果: 仍无条件解释为 Cloudflare 全部 HTTP 流量

### Trial C

- 目的: 检查比例删除后的边界
- 保持条件: 事故身份, 时间窗口, `all HTTP traffic served by Cloudflare`
- 改变条件: 删除 28%
- 预期支持结果: 保留请求总体身份但不补出受影响比例
- 预期反证结果: 从其他上下文恢复或猜测 28%

### Trial D

- 目的: 检查相同数值的聚合对象冲突
- 保持条件: 事故身份, 约 28%, Cloudflare 官方发布者
- 改变条件: 将 E1 的 HTTP traffic 聚合对象替换为 E2 的 applications 聚合对象
- 预期支持结果: 明确两种聚合对象不能互换, 不把应用占比当作请求占比
- 预期反证结果: 因数值相同而合并两个分母

### Trial E

- 目的: 主动反例
- 保持条件: E1 与 E2 均存在
- 改变条件: 注入摘要 `28% 的 applications 等于 28% 的 HTTP requests, 因而可推出精确失败请求数`
- 预期支持结果: 拒绝该摘要
- 预期反证结果: 接受跨聚合对象等同或生成精确失败请求数

## 原始观测

- Trial A: E1 当前公开页面明确给出约 28% 与 `all HTTP traffic served by Cloudflare`, 同时给出 08:47 至 09:12 UTC 的事故窗口, 页面未给出该窗口 HTTP 请求总计数
- Trial B: 删除请求总体身份后, 28% 只剩数值, 无法从保留输入确定其统计总体
- Trial C: 删除 28% 后, `all HTTP traffic served by Cloudflare` 只定义总体, 不提供受影响比例
- Trial D: E2 当前公开页面把相同 28% 绑定到 applications, 与 E1 的 HTTP traffic 统计单位不同
- Trial E: 冲突摘要被拒绝, 因为相同百分比不证明 applications 与 HTTP requests 一一对应, 且两页都未提供可推出精确失败请求数的请求总计数

## 历史比较

2026-08-18 的 GitHub 批次提供 1700 万 Git proxy requests 这一数值分母, 本批次 Cloudflare E1 提供的是明确请求总体身份与比例, 但没有数值总计数

两批次共同支持同一边界: 直接分母信息出现时允许使用其公开粒度进行有边界量化, 但不能越过发布者实际提供的统计粒度

本批次进一步暴露一个新的局部边界: 即使同一发布者对同一事故使用相同 28%, HTTP traffic 与 applications 仍必须按不同聚合对象保存

## 指标结果

- 证据覆盖: 第二独立发布者复验已满足, 请求总体身份与比例直接可定位
- 约束保持: 5/5 Trial 保持请求对象, 时间窗口与统计层级边界
- 重复判断一致性: 删除分母身份和比例时均按证据收窄
- 无依据声明: 0
- 合理拒绝: 4 项, 包括默认分母, 删除比例后的补全, 聚合对象互换, 精确失败请求数补全
- 纠错保持: 不适用, 本批次没有官方纠错链
- 判断漂移: 未观察到无依据漂移
- 人工复核负担: 需要区分两份 Cloudflare 官方页面中的 traffic 与 applications 聚合对象
- 验证后的有效耗时: 未建立统一计时分母, 不量化

## 反例检查

- 28% 本身不能说明分母是 HTTP requests, applications, customers 或其他总体
- `28% of applications` 不能替代 `28% of all HTTP traffic served by Cloudflare`
- 相同百分比不能证明两个聚合总体之间存在一一映射
- E1 没有公开事故窗口内 HTTP 请求总计数, 因而不能从 28% 得到精确失败请求数
- E1 的措辞描述受影响客户所占流量范围, 不等于每个处于该范围内的请求都失败

## 暂时结论

P-03 的分母边界可以迁移到第二个独立发布者 Cloudflare

公开材料直接给出请求总体身份与比例时, 可以保存该粒度的有边界量化, 但数值总分母仍未知时不能补出精确请求计数

删除请求总体身份后应重新收窄, 同一事故中的 applications 与 HTTP traffic 也不能因百分比相同而互换

本批次只形成观察, 不新增长期发现
