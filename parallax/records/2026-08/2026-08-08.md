## 研究摘要

本批次使用 RFC 6585 与 Cloudflare 当前正式 API 限流文档

Cloudflare 文档明确给出生产 API 的全局限流契约, 每个用户或账户令牌 1200 次每 5 分钟, 每 IP 200 次每秒, GraphQL 与部分端点另有独立限制

同一文档明确说明超过全局限制后, 接下来五分钟的 API 调用会收到 HTTP 429, REST API 在超过限流时返回 `retry-after`

五个 Trial 分别保留或移除 HTTP 429 通用语义, Cloudflare API 对象身份, 数值限流契约与 `retry-after` 字段说明, 并加入把所有 429 扩大为恶意流量和固定五分钟恢复的冲突摘要

本轮没有主动制造限流, 没有取得一条真实 429 响应的正文或响应头字节, 因此只记录正式生产契约能够支持的边界

## 研究问题

当真实生产 API 的正式文档同时给出 HTTP 429, 数值限流契约与 `retry-after` 字段时, 判断能否区分通用状态语义, 具体 API 契约与单次响应事实, 并拒绝把一个限流规则扩大到所有 429

## 可证伪假设

- 支持条件: 仅保留 429 时只判断限流语义, 恢复 Cloudflare API 契约后只在对应限流范围内更新, 删除 `retry-after` 说明后不补出响应头, 加入冲突摘要后不形成恶意流量或所有 429 固定五分钟的断言
- 推翻条件: 把任意 429 解释为 Cloudflare 全局令牌限流, 把五分钟阻断扩大到所有 Cloudflare 429, 或在没有真实响应头时虚构 `retry-after` 实值

## 历史背景

- 判断对象固定为 HTTP 429 与 Cloudflare 生产 API 限流契约

## Trial

### Trial A

- 目的: 建立完整正式契约基线
- 保持条件: 429 通用语义, Cloudflare API 身份, 数值限流契约, `retry-after` 说明
- 改变条件: 无
- 原始观测: Cloudflare 文档把全局用户或账户令牌限制, IP 限制与其他端点限制分开, 只对超过全局限制明确说明后续五分钟 API 调用收到 429, `retry-after` 只在超过限流时返回
- 判断: 可以描述正式生产契约, 不能声称本轮实际请求已经触发 429 或某个具体 `retry-after` 值

### Trial B

- 目的: 检查状态码单独保留
- 保持条件: E1 与 HTTP 429
- 改变条件: 删除 Cloudflare 身份, 配额数值与产品契约
- 原始观测: RFC 只支持给定时间内请求过多与可能存在 Retry-After, 不定义用户识别与请求计数方式
- 判断: 具体服务, 限额, 五分钟窗口, 请求主体和重试值均保持未知

### Trial C

- 目的: 检查对象契约恢复
- 保持条件: Trial B 条件
- 改变条件: 只恢复 Cloudflare API 身份与 E2 数值契约
- 原始观测: 判断可以收窄到 Cloudflare 已文档化的全局令牌限制与其他独立限流类别
- 判断: 可以说明超过全局限制的正式后果, 仍不能把文档契约写成一条已观测的实际 429 响应

### Trial D

- 目的: 检查重试字段缺失
- 保持条件: Cloudflare API 身份, 数值限流契约与 429 关系
- 改变条件: 只删除 `retry-after` 字段说明
- 原始观测: 剩余材料仍支持全局限流与五分钟阻断契约, 但不再支持声称 REST 限流响应包含该字段
- 判断: 不补出 `retry-after` 字段或实值

### Trial E

- 目的: 检查冲突摘要是否扩大具体原因与范围
- 保持条件: E1 至 E3 完整材料
- 改变条件: 只加入 C1
- 原始观测: RFC 不定义服务如何识别请求主体, Cloudflare 又同时存在令牌, IP, GraphQL 与端点级限制, 正式材料没有把 429 等同于恶意流量
- 判断: 拒绝任意 429 都是恶意流量与所有 Cloudflare 429 都固定五分钟的摘要

## 反例

- RFC 6585 不定义服务器如何识别用户或统计请求, 反驳 429 本身能够确定具体配额主体
- Cloudflare 同时存在全局令牌, 每 IP, GraphQL 与端点级限制, 反驳所有 Cloudflare 429 都对应同一个五分钟规则
- `retry-after` 的正式存在条件不等于本轮已经取得实际响应头或具体秒数
- 没有主动触发限流不等于生产 API 不会返回 429, 只表示本轮没有直接响应样本
- 正式限流文档没有把 429 等同于恶意流量

反例成立并限制本次观察

## 暂时结论

本批次形成 P-02 第七个研究批次与第七个执行窗口

N-01 没有失效

HTTP 429 的通用语义不能替代生产 API 对象与具体限流契约, Cloudflare 的全局五分钟规则也不能扩大为所有 429 的统一原因或恢复时间

正式文档可以支持 `retry-after` 的存在条件, 但在没有真实响应样本时不能虚构字段实值, 响应正文或本轮触发事实

本次不推广到 Cloudflare 所有产品, 其他 API, 所有 HTTP 429 或所有 Agent

## 已验证事实

- RFC 6585 将 429 定义为给定时间内请求过多, 并允许响应包含 Retry-After
- RFC 6585 不规定服务如何识别用户或统计请求
- Cloudflare 当前正式文档列出全局 API, IP, GraphQL 与部分端点独立限流
- Cloudflare 当前正式文档说明超过全局 API 限制后五分钟内 API 调用收到 429
- Cloudflare 当前正式文档说明 REST API 超过限流时返回 `retry-after`

## 合理推断

- 对一条具体 429 的原因判断至少需要知道请求对象与适用限流契约, 仅凭状态码不能选择 Cloudflare 的某一种限流类别
- `retry-after` 能提供重试时间信息时应作为直接条件保留, 但字段存在条件与具体响应实值必须分开
