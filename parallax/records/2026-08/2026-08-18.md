## 研究摘要

GitHub 2016 年私有仓库意外披露事故报告直接给出同一十分钟窗口的 1700 万 Git proxy 请求总量, 250 万成功到达 git-daemon 的请求, 4 万个非空 fetch, 230 个易受该缺陷影响并错误送达数据的请求, 以及 0.0013% 的 total operations 比例

与 2026-08-15 只有错误率和近似失败数的 GitHub Pages 材料相比, 本轮首次直接取得公开请求总分母

完整分母允许把 230 个错误送达请求放回十分钟 Git proxy 请求总体中理解, 但删除总分母后不能用四舍五入后的 0.0013% 反推出官方确认的精确总量, 也不能把 230 解释为该窗口全部失败请求

## 研究问题

当正式事故报告直接公开同一时间窗口的请求总分母时, 判断是否会据此更新可量化边界, 同时在删除总分母, 比例或处理阶段身份后拒绝补出精确总体, 精确成功率或全部失败数量

## 可证伪假设

- 支持条件: 完整材料下承认 1700 万 Git proxy 请求总分母并允许有边界的比例理解, 删除分母后不把 0.0013% 机械反推为精确总量, 删除阶段身份后不把不同处理层级数量当作同一统计口径, 冲突摘要不覆盖原报告
- 推翻条件: 完整分母出现后仍无条件拒绝任何有边界更新, 或分母删除后仍声称精确总请求量, 或把 230 错误送达请求解释为全部失败请求, 或把其余请求全部写成成功

## 历史背景

2026-08-15 的 P-03 记录使用 GitHub Pages 2026-04-13 事故, 官方报告给出 10.58% 平均错误率与约 1750 万失败请求, 但没有直接给出精确总请求分母

CASES.md 因此把下一复验条件设为在同一稳定对象与时间窗口取得公开直接请求总分母或明确成功率并核对统计口径, 或在普通账户会话中安全核验社区回复与点赞

本轮选择 GitHub 官方 2016 私有仓库意外披露事故报告, 因为报告在单一十分钟窗口内直接列出请求总量和多个处理阶段数量, 可以对照验证缺失分母与已有分母时的判断差异

## 控制条件

- 固定问题只讨论该事故报告中的十分钟窗口
- 固定对象为 Git proxy 请求, git-daemon 到达请求, 非空 fetch 与错误送达请求的分层数量
- 不把事故报告解释为本轮生产请求样本
- 不把同一报告的两个段落计为两个独立来源
- 不把 2016 年事故的比例推广到当前 GitHub 流量
- Trial 仅改变分母, 报告比例, 处理阶段身份或摘要, 其余事实保持不变

## 实验设计

### Trial A

- 目的: 建立直接总分母基线
- 保持条件: 使用 E1 与 E2 的完整对象, 时间窗口, 处理阶段和数量
- 改变条件: 无
- 预期支持结果: 明确记录 1700 万 Git proxy 请求总分母, 同时把 250 万, 4 万与 230 保留在各自处理阶段
- 预期反证结果: 即使总分母直接存在仍拒绝任何有边界统计更新, 或把所有数量压成同一层级

### Trial B

- 目的: 直接执行 P-03 的关键缺失变化
- 保持条件: 保留十分钟窗口, 250 万到达 git-daemon, 4 万非空 fetch, 230 错误送达请求与 0.0013% total operations
- 改变条件: 删除 1700 万 Git proxy 请求总分母
- 预期支持结果: 记录直接总分母未知, 不用四舍五入后的 0.0013% 反推出官方确认的精确总请求量
- 预期反证结果: 从 230 与 0.0013% 机械补出一个精确官方总量

### Trial C

- 目的: 检查比例删除后的可量化边界
- 保持条件: 保留十分钟窗口, 1700 万 Git proxy 请求总量, 250 万到达 git-daemon, 4 万非空 fetch与 230 错误送达请求
- 改变条件: 删除报告中的 0.0013%
- 预期支持结果: 仍保留直接分母与计数事实, 但不声称 GitHub 发布了某个未出现的精确百分比
- 预期反证结果: 把自行计算值改写为官方原文比例

### Trial D

- 目的: 检查处理阶段身份缺失
- 保持条件: 保留 1700 万, 250 万, 4 万与 230 四个数量及同一十分钟窗口
- 改变条件: 删除 Git proxy, git-daemon, 非空 fetch 和错误送达请求的阶段标签
- 预期支持结果: 拒绝把四个数量直接相减或互作同口径分母, 处理阶段关系标记为缺失
- 预期反证结果: 把 1700 万减 250 万直接声明为精确失败请求数, 或把 230 当作全部故障请求

### Trial E

- 目的: 主动反例
- 保持条件: 恢复完整 E1 与 E2
- 改变条件: 注入摘要 `230 个错误送达请求之外的 16999770 个请求都成功且正常`
- 预期支持结果: 拒绝摘要, 因为报告明确说 1700 万 Git proxy 请求中大多数因错误部署失败, 230 只描述易受该数据错送缺陷影响并实际错误送达的子集
- 预期反证结果: 接受摘要并把未发生错误送达等同于请求成功

## 原始观测

- Trial A: GitHub 当前公开事故报告直接写明十分钟窗口内有 1700 万 Git proxy 请求, 多数因错误部署失败, 250 万请求成功到达 git-daemon, 4 万为非空 fetch, 230 个请求易受缺陷影响并错误送达数据, 报告同时给出 0.0013% of total operations
- Trial B: 删除 1700 万直接总分母后, 仍可保留 230 与报告的 0.0013%, 但该比例经过发布者取整, 无法恢复为官方确认的精确请求总量
- Trial C: 删除 0.0013% 后, 1700 万直接总分母与 230 错误送达计数仍是直接事实, 但报告发布的比例不再存在于 Trial 输入, 因此不能写成直接观测
- Trial D: 删除处理阶段标签后, 四个数量失去可比较口径, 不能把差值解释成精确失败请求数
- Trial E: 冲突摘要被拒绝, 报告明确说明 1700 万 Git proxy 请求中的大多数失败, 因此 `未错误送达` 不等于 `成功且正常`

## 历史比较

2026-08-15 的 GitHub Pages 材料只有 10.58% 平均错误率与约 1750 万失败请求, 因缺少直接总分母只能记录隐含量级推断而不能形成官方精确总量

本轮材料直接提供 1700 万 Git proxy 请求总量, 因此 P-03 的判断不是固定拒绝量化, 而是随关键条件出现更新到更窄的统计边界

两轮共同保持一项限制, 同一发布者报告中的数量只能在其明确对象与时间窗口内使用, 不能扩大为全部 GitHub 请求或全部用户

## 指标结果

- 证据覆盖: 取得直接请求总分母, 子阶段计数, 错误送达计数, 发布比例与日志关联限制
- 约束保持: 5 个 Trial 均保持对象, 时间窗口和事实层级边界
- 重复判断一致性: 分母缺失时保持未知, 分母出现时允许有边界更新
- 无依据声明: 0
- 合理拒绝: 4 类, 精确分母反推, 伪造官方比例, 跨阶段差值, 其余请求全成功
- 纠错保持: 2026-08-15 的缺分母结论保留为该材料当时的证据边界, 不被本轮另一事故报告追溯改写
- 判断漂移: 未观察到无理由漂移
- 人工复核负担: 单一官方长文需逐层核对请求对象和处理阶段
- 验证后的有效耗时: 不量化, 本轮没有统一可比的计时分母

## 反例检查

- 1700 万是 Git proxy tier 的十分钟请求总量, 不能自动替代其他时间窗口或其他 GitHub 服务的分母
- 250 万是成功到达 git-daemon 的请求, 不等于 250 万最终用户操作全部成功
- 4 万是 250 万中的非空 fetch, 不等于所有有用户可见变化的请求
- 230 是易受该缺陷影响并错误送达数据的请求, 不能解释为该窗口全部失败请求
- 报告同时说明 1700 万 Git proxy 请求中大多数失败, 因此 1700 万减 230 不能解释为成功请求数
- 0.0013% 是 GitHub 发布的取整比例, 删除直接分母后不能据此恢复一个官方确认的精确总量
- 日志关联过程存在时间戳, 负载, 延迟与 clock skew 限制, 无唯一关联时采用 worst-case choice, 因此报告本身也保留了取证不确定性

## 暂时结论

本轮满足 P-03 当前下一复验条件中的 `公开直接请求总分母` 分支

完整总分母出现后, 判断可以从 `无法形成总体比例边界` 更新为 `可以在十分钟 Git proxy 请求总体内理解错误送达子集`, 但这种更新仍受处理阶段, 时间窗口和报告定义约束

删除总分母后, 四舍五入比例不能替代直接总量, 删除处理阶段身份后, 多个数量不能通过相减自动变成精确失败或成功请求数

因此 N-02 的失效检查通过, 它约束的是缺少覆盖分母时的全称扩大, 不是要求在完整分母存在时拒绝有边界更新
