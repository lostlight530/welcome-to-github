## 研究摘要

本日研究 OpenAI Agents SDK Python 的 local MCP adapter, 问题不是工具是否需要 approval, 而是 callable `require_approval` 能看到什么调用身份, 能否依据每次调用的具体 arguments 与 call ID 实施 per-call authorization

官方 `docs/mcp.md` 给出的 callable 签名是 `(run_context, agent, tool)`, 并明确说明它不会收到具体调用的 arguments 或 call ID; `src/agents/mcp/server.py` 将该策略包装成 `FunctionTool.needs_approval` 时显式忽略 `_args` 与 `_call_id`, 只把 `run_context`、`agent` 和原始 MCP `Tool` 传给策略

若直接调用 `MCPUtil.to_function_tool()` 而不提供 `agent`, callable policy 不会执行, adapter 将 approval 设置为 required, 这是兼容路径上的 fail-closed fallback

SDK 另有 per-call `tool_input_guardrails` 与 `tool_meta_resolver`, 前者可在 MCP server call 前阻止调用, 后者可读取 parsed arguments 并生成请求 `_meta`; 二者都不能被误读为 `require_approval` callback

上游 CI 实际执行了 `tests/mcp/test_mcp_util.py` 所在测试模块, 结果为 PARTIAL, 因为测试使用 SDK fixture, 没有真实远端 MCP server 或应用侧授权效果

## 研究问题

在 OpenAI Agents SDK Python 的 local MCP adapter 中, `require_approval` callable 是否获得每次工具调用的具体 arguments 与 call ID, 从而能独立实施 argument-sensitive authorization? 若不能, 哪些其他 hook 能读取 per-call arguments, 它们各自承担什么语义?

## 可证伪假设

- 支持条件: local MCP `require_approval` callback 收到本次调用的 parsed arguments 与 call ID, 且策略可据此区分同一 tool name 的不同请求
- 推翻条件: callback 只收到 `run_context`、`agent` 与原始 MCP `Tool`; adapter 丢弃 per-call arguments 与 call ID; legacy direct conversion 在没有 agent 时不调用 policy 并 fail closed

## Identity boundary

```text
LOCAL_MCP_REQUIRE_APPROVAL
= (run_context, agent, original_mcp_tool, tool_annotations)
!= (specific_call_arguments, call_id)

FUNCTION_TOOL_NEEDS_APPROVAL
= (run_context, parsed_arguments, call_id)

MCP_TOOL_META_RESOLVER
= (run_context, server_name, tool_name, parsed_arguments) -> outbound _meta

MCP_TOOL_INPUT_GUARDRAIL
= per-call ToolContext / tool_arguments -> allow, reject or replacement content
```

`require_approval` 是 local MCP server/tool-level approval policy, 不等于 argument-sensitive per-call authorization; `tool_meta_resolver` 是 request metadata enrichment, 不等于 authorization; `tool_input_guardrails` 是 per-call validation gate, 不等于 approval decision

`tool.annotations` 由 MCP server 提供, 官方文档将其定义为 advisory hints; 只有应用信任该 server 的 classification 时, 才能据此 bypass approval

`HostedMCPTool` 由 Responses API 执行, 不属于本轮 local MCP server contract

## 原始观测

1. `docs/mcp.md` documents callable `require_approval` as `(run_context, agent, tool) -> bool | Awaitable[bool]`
2. The same document explicitly states that a local MCP policy does not receive the specific call arguments or call ID
3. `src/agents/mcp/server.py` defines `_needs_approval(run_context, _args, _call_id)` and invokes `policy(run_context, agent, tool)`; the adapter parameters `_args` and `_call_id` are unused
4. The same source returns `True` when `agent is None`, so the callable policy is not invoked and approval remains required
5. `src/agents/mcp/util.py` passes the server approval value to the converted `FunctionTool` and attaches copied server-wide input/output guardrail lists to each converted tool
6. `MCPToolMetaContext` has an `arguments` field; `_resolve_meta` passes parsed arguments to `tool_meta_resolver` and returns its dictionary as MCP request metadata
7. `docs/mcp.md` states that local MCP input guardrails can prevent the server call and that hosted MCP tools do not receive these client-side guardrails
8. `tests/mcp/test_mcp_util.py` contains cases for callable policy inputs, no-agent fail-closed fallback and guardrail attachment

## 反例检查

若 `require_approval` 真正具备 per-call arguments 与 call ID, 同一 tool name 的两个不同 payload 应能被 callback 分别判断; 当前 adapter wrapper 不传入这些字段, 因此不能仅凭该 callback 对 `path`, `record_id` 或其他参数值作出不同 approval decision

这不意味着 SDK 完全没有 per-call input control: `tool_input_guardrails` 可读取 `ToolContext.tool_arguments` 并在 server call 前阻止调用, 但它是 validation gate, 不是 `require_approval` callback

`tool_meta_resolver` 也能读取 parsed arguments, 但它负责产生 outbound MCP `_meta`; metadata enrichment 不是授权结论, 不能把其返回值当作 approval receipt

MCP annotations 是 server-provided advisory hints, 如果 server classification 不可信, 用它 bypass approval 会把不可信 metadata 提升为授权事实

legacy direct conversion without agent 是额外负控制: 即使 callable policy 的测试实现返回 `False`, adapter 仍返回 `needs_approval=True`, 不调用 policy, 保持 fail-closed

## 暂时结论

PARTIAL, 当前假设被推翻于 OpenAI Agents SDK Python local MCP adapter

local MCP `require_approval` callable 是 agent/tool-level policy, 不是 argument-sensitive per-call authorization; adapter 把它包装为 `FunctionTool.needs_approval` 时丢弃 `_args` 与 `_call_id`; 无 agent 的 legacy direct conversion 不执行 callable policy, 而是要求 approval

per-call input validation 由 `tool_input_guardrails` 承担, per-call outbound metadata 由 `tool_meta_resolver` 承担, 两者不能替代 approval semantics; 上游 CI 证明相关测试模块在固定 commit 上实际执行, 但没有真实远端 MCP server、应用授权策略或外部 effect evidence

## AGI-scale relevance boundary

长期自主 Agent 通过 MCP 将权限委托到外部 server 时, approval policy、per-call resource validation 与 request metadata 必须保留不同 identity; tool name 或 server annotation 不足以代表具体资源操作, metadata enrichment 也不能替代 host-owned authorization

本研究只指出一个 SDK adapter contract boundary, 不构成 Agent 已具备或缺乏 AGI 能力的证据
