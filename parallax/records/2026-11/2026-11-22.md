## 研究摘要

This native Daily tests whether returning from a buffered Agent session append is the same event as completion of durable delegate storage. Pinned official Google ADK source places the live-session apply and queueing path before the asynchronous delegate append, while flush and close await outstanding writes and surface persistence errors. The current documentation explicitly identifies crash-loss and event-loop lifetime boundaries. A bounded source-evidence procedure ran twenty-five JavaScript assertions successfully after correcting one whitespace-only harness mistake. The supported outcome is a source-level contract boundary, not an observed ADK application execution.

## 研究问题

Does successful return from an awaited BufferedSessionService.append_event imply that the wrapped BaseSessionService already stored the event durably, and which observable operations establish a stronger persistence boundary?

## 可证伪假设

- H0 to test: a successful await of BufferedSessionService.append_event is itself a delegate-store completion receipt
- H0 supporting source evidence: its return path must await successful delegate append or equivalent store flush before yielding control
- H0 counterevidence: live-session apply plus queue append can return before asynchronous writer invokes the delegate, with separate flush and failure paths
- Narrow alternative: append acceptance, in-memory state mutation, buffered queue state, delegate persistence and downstream recovery are distinct identities

## 原始观测

- Pinned Google ADK main SHA 2b90353cd2f1ee0a8a52262a7843333b6f7d2c8d and 8 directly fetched artifact blob SHAs in E1-E8
- BufferedSessionService declares experimental feature BUFFERED_SESSION_SERVICE and default retry_config max_attempts=1
- Buffered append_event ignores partial events, snapshots other events, calls buffer.append and applies event to local Session
- Buffer append calls apply, queues a write and returns appended, while a separately created writer eventually calls the delegate append_event or append_events
- get_session waits on writes it would see and then calls the delegate get_session; the official guide states a read never raises a write failure
- flush_session awaits one session's pending writes, flush awaits all writers, aclose flushes then stops writers

- The guide states unpersisted writes are lost on crash and Runner.run may close its event loop with writes still in flight

## 反例检查

The strongest objection to a global claim of non-durability is that buffered reads wait for relevant writes, flush can complete successfully, and the background writer may already persist before a later caller inspects the session. These counter-controls refute the stronger but unsupported assertion that every append return always precedes backend storage. They do not rescue the narrower H0 that append return alone guarantees it. Another limitation is that source and test definitions could differ from behavior in a deployed version; no store fault injection or post-crash readback was executed.

## 暂时结论

PARTIAL: pinned Google ADK source and documentation support a distinct acceptance-versus-persistence contract for experimental BufferedSessionService. The appending caller can receive a local Session update and enqueue acknowledgement without a required delegate-store completion receipt; flush and failure paths give stronger documented guarantees but were not executed here. Neither actual persistence latency, crash-loss frequency, retry correctness under a real delegate, production enablement nor end-to-end application settlement is established. No CASE support, candidate, NOTES promotion, Special or Audit.

## AGI-scale relevance boundary

A durable Agent runtime needs explicit identities for in-memory event application, queued write, delegate commit, flush completion, read-back and recovery evidence. A tool return or event acknowledgement alone cannot certify state continuity across failures. This research addresses evidence integrity and human handoff contracts, not measured AGI capability or generalized ADK reliability.
