## 研究摘要

本轮在一个确实完成且整体为 success 的 GitHub Actions workflow 中观察到一项 success Job 与另一项 skipped Job 共存, 以同一 commit 和同一 workflow run 的直接 Job API 记录检验 aggregate success 是否蕴含所有 Job 都实际执行成功, 结果为否, 这是一项有对象和执行身份约束的只读观察, 不是对 skipped Job 的运行时重放

## 研究问题

在同一个固定 commit 和同一个 workflow run 中, `conclusion=success` 是否足以推断每一个已列 Job 都实际执行并成功完成

## 可证伪假设

- 待反驳假设 H0: workflow run 成功意味着该 run 的所有已列 Job 均具有 `conclusion=success` 且实际执行
- 支持条件: 直接读取的每个 Job 均为 completed/success, 且步骤证据支持实际执行
- 推翻条件: 同一成功 workflow 的直接 Job 列表存在 completed/skipped
- 有界替代判断: workflow aggregate conclusion, job conclusion, job step execution 与 downstream application effect 必须保留不同身份

## 历史背景

2026-11-21 的研究将 commit directive 与触发事件和 CodeQL Job 分开, 2026-11-22 的研究则以 Google ADK 源码区分事件接受和持久结算, 本轮返回 GitHub 原生 workflow-run 与 job-level 事实, 使用一个实际同 run 的正反例, 不重写前两日证据

## 实验设计

### Trial A

- 目的: 检验 aggregate workflow success 是否蕴含同一 run 的全部 Job success
- 保持条件: 同一个 run 45029811626, 同一个 commit, 同一读取时点的 completed 状态
- 改变条件: 将观测单位从 workflow run 缩小为其两个 Job
- 预期支持结果: 两个 Job 均 completed/success
- 预期反证结果: 一个 Job completed/success, 另一个 completed/skipped

### Trial B

- 目的: 检验能否从同 commit 的其他成功 workflow 补全被跳过的 Job
- 保持条件: 同一 main commit
- 改变条件: 观测对象从 run 45029811626 转为同 commit 的 Deploy 与 CodeQL runs
- 预期支持结果: 其他 run 的 success 可以提供同一 Job ID 的执行回执
- 预期反证结果: 其他 run 拥有不同 run/job identity, 无法替代 137230686195 的执行证据
