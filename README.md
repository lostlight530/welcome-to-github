## Engineering and Research Principles

Across the public repositories, a few principles remain deliberately stable:

- **Evidence before narrative**: implementation, source identity, observed execution, interpretation, and inference are kept separate where they materially differ.
- **Reproducible identity**: revisions, artifacts, sources, dates, and runtime observations are identified explicitly rather than inferred from filenames or later state.
- **Bounded claims**: a successful command, checker, render, source retrieval, hash, citation, or DOI supports only the property it actually demonstrates.
- **Historical preservation**: later corrections refine current interpretation without silently rewriting point-in-time research history.
- **Human-review boundary**: automation and AI assistance can research, generate, validate, and maintain, while public evidence and final repository changes remain inspectable and reviewable.
- **Independent repository identity**: the ten projects share research concerns but retain their own architecture, contracts, evidence semantics, and release history.

## Engineering Standards and Architecture

This repository remains the entry point for an edge-first research system and a deterministic knowledge lifecycle.

- **Bilingual Accessibility**: Chinese navigation and English technical content remain readable without requiring a specialized client.
- **Standard-Library Core**: The Python lifecycle uses the standard library. Explicitly declared browser assets may be delivered separately by the presentation layer.
- **Append-Only Evidence**: Historical evidence is retained under the archive policy while active indexes remain reproducible from canonical ledgers.
- **Validation Boundary**: Untrusted observations are accepted only after provenance, format, lifecycle, and human-review checks. This is a repository policy boundary, not a public network security service.
- **Continuous System Pulse**: Scheduled and change-triggered checks keep the current repository state testable and auditable.

## Citation and Reuse

Each repository exposes its own citation and release metadata where applicable. Use the repository-specific DOI above when citing an archived software publication, and use the relevant repository revision when reproducibility depends on exact implementation state.

A DOI establishes a stable publication identity; it does not by itself establish scientific validity, runtime reproduction, or equivalence with later repository revisions.
